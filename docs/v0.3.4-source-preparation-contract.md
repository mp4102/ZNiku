## 1. 身份与职责

产品版本为 0.3.4。以下全部新节点 exact version 为 `0.3.4`；旧 `0.2.1/0.3.2/0.3.3`
定义不修改、不迁移。Project SQLite schema 4、原 Project Service/Presentation wire 0.3.0 不变。
准备专属 HTTP wire 为 0.3.4。

共存目录已达到 60 个定义、46 种 Schema；既有成功语法检查缓存由 32 项扩为 128 项，
每项仍最多 256 KiB（键总量上限 32 MiB）。只减少重复语法检查，不缓存节点参数验证、
失败结果或 Runtime 结论，不改变 Core 合同及持久格式。

| type_id | 直接输入 | 输出 | 职责及必要参数 |
| --- | --- | --- | --- |
| `zniku.source_preparation.source` | 无 | `media:MediaFile` | `source_path` 指定只读实体原件；不先要求 CFR，不复制 |
| `zniku.source_preparation.diagnostics` | `original_media:MediaFile` | `diagnosis:DataFile` | 完整 EOF 检查；`target_frame_rate` 是明确有理数或 null |
| `zniku.source_preparation.video_prepare.t1` | 原件＋诊断 | `media:MediaFile` | 固定 `strategy_id=t1-clock-quantization/1`、精确目标率；生成并完整验收新 MKV |
| `zniku.source_preparation.video_repair.external.{mkv,mp4,mov}` | 原件＋诊断 | `media:MediaFile` | 三个独立 exact 定义、各一个输出；显式提交后完整保内容检查 |
| `zniku.source_preparation.admission` | 原件、`reference_media`、有序 `audio_sources`、诊断 | `video:VideoFile`＋`gate:DataFile` | 对已登记参考独立准入；`audio_policy=original/none`；none 只适用于原件确实无音轨 |

`zniku.source_preparation` 负责原件检查及准备；`zniku.prepared_source` 负责从已准入参考开始的业务节点。
后者使用 `zniku.prepared.overlap.*` 的 Split/Enhancement/Merge/Context/FI/Crop/Program/Final，
MR 使用 `zniku.prepared_source.external.{mp4,mov,mkv}`。动态 Split 的精确端口数仍由 Python 声明。
机器盘点见[新 Schema corpus](architecture/studio-prepared-source-schema-corpus.json)，它不是额外语义权威。

## 2. 四类来源与绑定

- `original_media`：只读原件，诊断和保内容比较对象；默认也作为音频载体。
- `reference_media`／`reference_video`：准备完成的实际媒体及准入后只读视频引用；规划仅使用该 N/FPS。
- `effective_video`：下游真正切分的视频；MR 关闭时是参考，开启时为明确的 MR 输出。
- `audio_sources`：有序直接输入及显式 stream index，不从 MR/增强/FI 文件偷换音频。

同一路径不意味着同一领域角色；不同路径也不能推断开启 MR。新节点参数显式保存 `mr_role`。
局部 metadata namespace 为 `zniku.source.prepared`。
诊断文档 schema 为 `zniku.source.prepared.diagnosis/1`，准入为
`zniku.source.prepared.admission/1`，均严格拒绝未知字段及非法 JSON。

gate 只引用已有 original/reference/diagnosis/audio Artifact ID；不预填它自己的未来视频输出 UUID。
reference video 与 gate 的关系由同一次准入输出、metadata 角色及当前直接输入核对。
原件音轨的相对偏移以 `original_video_start` 为基准，不减去修复后重新起算的 reference start。

## 3. 诊断与首发白名单

诊断完整完成但发现不兼容时，节点成功产生问题报告；它不等于工作源准入。
取消、超时、工具缺失、输入变化、未读到 EOF、损坏报告不能登记成功诊断。
报告保存完整扫描范围、工具版本、输入前后 stat、视频/音频时钟和解码错误事实。
各 adapter 和 validator 都先匹配完整 exact definition，而不只验证 type_id/version 或 validator 名字；
自定义 manual 节点不能借用报告 validator 伪造正式诊断或准入 metadata。

首发媒体入口限定本地实体 MKV/MP4/MOV，拒绝符号链接、junction、播放列表、外部协议；
FFmpeg/FFprobe 使用固定 demuxer 和 file 协议 allowlist。
一条逐行 H.264/yuv420p 视频，方形像素、零旋转、SDR；额外流、章节和不明信号不自动丢弃或猜测。
默认支持无音频，或已证明没有 skip/discard/负首包等 priming 问题的 AAC 音轨。
PCM/FLAC 转换、priming 保持、T3、HDR、非方形像素和不能保持的属性不在首发范围。

目标率是 1–240 之间约分后的精确有理数。自动默认仅在 header 两种率一致且合法时出现；
有歧义时必须显式选择。重新选择目标率会重新运行诊断，不能以 UI 字段代替实际检查。
`video.bitstream_clock` 另记录 H.264 容器 extradata 与首包的 SPS 观察，明确标为 `scope=initial-sps`；
读取受 60 秒、有限日志、有限 SPS 数及取消边界约束。明确 fixed VUI 与目标冲突时拒绝；
无法解析或相互矛盾时不能假装已查明。`fixed_frame_rate_flag=0` 不被猜成固定时钟冲突。
此观察不证明全片没有 SPS 切换；完整帧序与内容扫描的范围和首包头检的范围分别记录。
容器 duration 只作观察，视频时长使用展示帧与参考率，不用容器最长音轨强行推算视频尾帧。

## 4. T1 的窄数学范围与晋级

候选必须只存在 CLOCK_NOT_CFR 问题，完整展示序和一包一帧关系可确认，
无缺失／重复／逆序／best-effort 替代 PTS，无解码错误。
逐帧比较实际 PTS 与 `first_pts + n / target_rate`：

- CFR 时钟容差为 max(2 × time_base, 1 微秒)，且必须小于四分之一目标帧。
- 允许进入 T1 的最大时钟误差严格小于四分之一目标帧；不是只比较首尾跨度。
- 超出范围、不明对应或需要 T3 映射时不运行 T1。

MKVToolNix 轨 ID 来自实际识别，不硬编码视频轨 0。固定 argv、shell=False，
通过 `--default-duration` 生成新候选；不存在直接写原件的接口。
候选再分别完成目标时钟检查、完整有序解码像素比较、全部音轨 f32le 样本比较、
媒体属性和相对音画起止关系核对（保内容前后相对差最大 2 ms）。
这些逐帧摘要仅属于本修复节点，不提升成 Core 的 digest/QC authority。

`T1_PROMOTED` 是产品代码的发布决定，Graph 参数和第三方报告不能开启它。
代表及留出真实素材尚未全部通过时保持 false；测试的局部模拟开关不是交付资格。
T3 和音频转换不提供可运行入口。

## 5. 执行、停止与归档

只读正常链不复制源视频；准备候选先留在 attempt staging，经本节点验证后才登记。
独立 Admission 随后再核对已登记输入，不在上游执行期间等待未来下游结果。
内置准备的 validator 仅核验受信 adapter 的当前输出事实，不重复完整内容扫描；
人工提交仍按实际文件重新完整验证，不接受第三方成功声明。

源检查、候选生成、完整比较使用可停止的流式子进程，不缓存全片帧表。
阶段日志记录实测帧／包／样本／字节、耗时及速度；无可靠分母时不显示百分比。
Project Service 的临时协作停止信号不进入 Core/SQLite，不增设运行状态。
停止请求先通知当前线程，退出前仍 busy；异常经现有 Runner 收敛为失败，
保留已完成节点，重试创建新 attempt，不提供节点内部 resume。
准备外部导入／readiness／Submit 的完整验证同样可发送停止信号。

工作数据仍使用既有可读持久布局：`attempts/common/素材检查__N###/R###-A###` 等；
准备输出命名为 `片名.source-prepared.mkv` 或 `片名.source-repaired.实际后缀`，
诊断和准入文件位于各自 reports 子路径。章节后续仍使用章/叶名；UUID 保留为真实身份。
成功中间产物不自动删除，不自动搬动旧工程或旧 attempt。

## 6. 服务与界面边界

`/api/studio/templates/prepared-source/` 的 create/view/choose/cancel/processing-preview/full-preview/expand
使用独立严格 wire。变更同一 Graph 时检查 session、CAS、当前图形状和已完成输入 Run；
纯 UI 位置变化不影响绑定，用户自由修改执行图后向导不得覆盖它。
创建、选择和展开不暗中执行媒体；启动仍通过普通 Run 命令。

`operation-view` / `operation-cancel` 是独立的当前操作入口，严格绑定 session、Run、
`node_run_id` 和 snapshot 内完整 exact definition；不依赖模板节点名或当前编辑图形状。
因此改名、加入合法分支或展开完整处理图后，仍可监控和停止实际活动的素材准备节点。
手工验证使用服务临时保存的明确 attempt 身份，不从多个 waiting 任务的顺序猜测；
自动执行使用当前唯一 RUNNING 受信准备节点。旧 attempt、另一 Run、未活动节点不得误停工作。
此视图只含阶段进度和协作停止信息，不含路线、准入或可规划来源字段；不能代替向导的图编辑门禁。
旧向导 `cancel` 保留兼容，按相同活动操作边界发送停止，不放宽 choose/expand。

外部导入保留原件，格式固定为一个当前 exact 定义；发现文件不自动提交。
不符合保内容承诺时，只能作为新工作源新建工程重新分析，不复用旧规划。
界面、profile 名称、Presentation、Schema corpus 均不产生新的媒体验收 authority。
Phase 5 外部 AI 软件及用户成品验收仍独立保留。

## 7. 已批准的色彩声明增量

产品版本仍为 `0.3.4`。同一组业务 type_id 并列提供 exact `0.3.4-color.1`，
新上游实现为 `zniku.source_color`，新下游为 `zniku.prepared_color`；完整 definition、
adapter/validator 及局部 namespace 分开，不把新 Gate 翻译成旧节点可消费的 Artifact。
18 个旧 exact 定义的完整 Schema/执行器形状另有固定兼容测试。

- 源报告升级为 `zniku.source.prepared.diagnosis/2`，准入为 `zniku.source.prepared.admission/2`，
  namespace 为 `zniku.source.prepared.color`。保存独立容器、完整参数集和完整解码帧观察；
  absent、explicit unspecified 与 unavailable 不合并，格式数字按其所属规范解释。
- Gate 保留已有真实 original/reference/diagnosis/audio 绑定，新增 `observed_signal`、
  `working_signal`、`interpretation_policy`、逐字段 `basis` 及 `policy_version=color-interpretation/1`。
  新字段不能填入旧 `/1` 报告；后续工作解释来自已绑定 Gate，不来自 UI 默认值。
- Admission 的严格 Graph 参数默认 `declared_only`；仅用户主动选
  `operator_confirmed_bt709_limited_left` 才能填补已证明未指定的项。
  已有明确值、冲突、全程变化、解析失败或不支持的 HDR/ICC/SEI 不能被覆盖。
- 准备与工作准入分离：新 T1 策略为 `t1-clock-quantization/2`，外部保内容策略为
  `external-preservation/2`。准备允许在严格内容/声明保持验证下保留未指定项，
  不替副本补标签；完整工作准入仍需明确工作解释及全部其他约束通过。
- 新服务前缀 `/api/studio/templates/prepared-color/`、wire `0.3.4-color.1`、profile
  `zniku.prepared-color-overlap@0.3.4-color.1`。原 prepared-source 端点和 wire 保留。
  改变工作解释只改同一图的 Admission 参数，按普通 reuse/stale 规则产生新 attempt；
  不接管活动交接、不重解释既有完成结果。
- Studio 直接显示工作解释选项和边界；修复成功不自动等于准入。
  外部增强/FI 缺标签时只能明确记为继承已绑定的工作解释，不声称为文件自身实测声明。

上述版本冻结与功能实现不等于 T1 晋级。真实代表、冻结后留出和实际下游准入仍须通过；
没有精确真实输入/策略/新输出写授权前，不生成真实候选，不修改用户工程或服务。
