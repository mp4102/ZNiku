## 1. 本次解决的问题

上一版把内部 `attempts/common/任务__N022/R003-A001/incoming/port-<hash>` 暴露给操作者。
中文标签改善了部分辨识，但没有消除内部编号、混合语言、长端口编码和多余层级。新方案直接简化实体目录，
不是另造一个展示目录、第二份大媒体或只靠 GUI 按钮隐藏旧布局。

磁盘目录使用英文，GUI 保持中文。节点、Run、attempt 和 port 的正式身份仍在 `.zniku` 内保存；文件夹名
只是持久存储定位，不是执行、媒体身份或 reuse/stale 的新依据。

## 2. 目录形状与命名

新布局按 `task/[chapter]/round-NNN/{incoming,outputs,logs}` 组织。下例使用合成工程名，不对应真实任务：

```text
Example.data/
├── .zniku-storage-owner.json
├── source-repair/
│   └── round-001/
│       ├── incoming/
│       ├── outputs/
│       └── logs/
├── chapter-split/
│   └── round-001/
│       ├── outputs/
│       │   ├── A/
│       │   ├── B/
│       │   └── C/
│       └── logs/
├── enhancement/
│   ├── A/round-001/{incoming,outputs,logs}/
│   ├── B/round-001/{incoming,outputs,logs}/
│   └── C/round-001/{incoming,outputs,logs}/
├── chapter-merge/
│   └── A/round-001/{outputs,logs}/
└── frame-interpolation/
    └── A/round-001/{incoming,outputs,logs}/
```

大括号仅为示意，不是实际目录名称。automatic 不需要交回区；人工节点进入等待前才创建本次交回目录。
其他节点沿用同样的任务目录规则，不要求每张 Graph 必须含这些步骤或章节。

| 稳定英文目录 | 用途 |
| --- | --- |
| `source-repair` | 外部源视频修复 |
| `chapter-split` | 分章与章内分叶 |
| `enhancement` | 画质增强 |
| `chapter-merge` | 章内增强结果合并 |
| `frame-interpolation` | 外部章节补帧 |
| `round-001` | 同一任务的第 1 次处理位置，跨 Run 持续分配 |
| `incoming` | 未提交的外部交回文件 |
| `outputs` | 正式声明输出位置；存在文件仍不等于已登记 Artifact |
| `logs` | 处理日志与技术记录 |

目录统一小写英文、连字符分词，章节标签使用已经声明的安全标签，例如 `A/B/C`。媒体文件继续沿用既定
点分命名，例如 `Example.A.leaf-0001.enhancement.mov`、`Example.A.enhancement.fi.mov`；不翻译文件名或
改变外部媒体合同。章级任务上层已有章节时，`outputs` 不再重复套同名章节文件夹；一次 Split 的多章输出仍保留
`outputs/A`、`outputs/B`。保留少量有固定用途的系统定位文件，不要求每个文件都成为操作者交付对象。

任务英文名称由可信 Python 宿主按 exact definition 提供纯命名提示；Runtime 不识别业务流程。未提供提示
的普通节点使用稳定英文回退名称。同名独立任务仅在冲突时分配短序号，首次分配后固化；不得恢复全局
`__N...`、Run/attempt 组合或端口哈希作为正常交付目录层级。

## 3. 身份、处理轮次与不可变定位

- 节点路径、必要的重名后缀、处理轮次与 NodeRun 绑定在同一 SQLite 事务持久化；失败回滚，不能留下
  半套映射。编号不来自目录扫描、当前画布排序或临时显示序号。
- `round-NNN` 属于稳定 node instance，跨 Run 连续，不是每个 Run 重置的 attempt 改名。每次从头处理使用
  独立目录，不能覆盖前一次结果。复用已完成结果不新建媒体目录、不复制媒体；内部历史记录仍保持正式
  NodeRun 关系，不将两个 attempt 工作目录绑定为同一目录。
- 实际开始新处理时才分配 round；尚未开始的 pending 和直接 reuse 允许保留独立 UUID 逻辑定位，但不在
  磁盘创建相应 UUID 文件夹。内部保留身份或逻辑路径，不等于让操作者面对 UUID 收件目录。读取历史不
  补分配，准备失败也不能留下可被错认成正式绑定的路径。
- 新建、复制和删除节点继续使用 Core 身份规则；复制的节点是独立任务。删除节点不回收原目录或媒体。
- 改 GUI 别名、拖动、分组、调整信息密度不重命名已分配目录，不影响 Graph、snapshot 或 reuse/stale。
- 不维护会自动搬家的 `current`/`history` 目录；GUI 的“打开交回目录”由当前绑定定位到固定 round。
- 一次 Split 的全部章叶保持在同一个独立 attempt 下。不能为了章优先的美观，把它拆成跨 attempt 媒体
  根或复制一份用于浏览的媒体。

## 4. 平铺收件与碰撞处理

单输出任务直接使用本轮 `incoming`，不再创建 `port-<hash>` 子目录。章级批量增强在章目录的 `incoming`
中接收多个规范命名文件，例如：

```text
enhancement/A/round-001/incoming/
    Example.A.leaf-0001.enhancement.mov
    Example.A.leaf-0002.enhancement.mov
```

多输出名称在 Windows 大小写折叠后必须仍唯一；规范文件名冲突时，服务端使用安全、可读且唯一的端口
子目录或短序号，并保持正式 port 绑定。不能只删除旧哈希编码，让不同输出相互覆盖；非法或任意 Graph
port ID 不得直接拼入磁盘路径。

文件出现只说明收到来件。UI 多选、目录导入和直接放入交回区都继续经过明确匹配/收纳、完整检查和显式
Submit。部分收件不登记部分 Artifact，不引入节点内 checkpoint，也不把等待时间换成外部完成进度。

原有用户文件始终保留。来自 attempt 外的文件仍复制；已经位于当前 attempt 专属收件区的文件可经确认
在同一 attempt 内受控转存，不为目录展示复制第二份大媒体。替换已有目标仍须明确确认，失败保留可恢复
来件和旧产物。未通过节点 validator 的 `outputs` 文件不能因名称或位置正确而视为成果。

## 5. 版本与旧工程边界

新目录使用 `ProjectStorage.contract_version="0.3.5"`、`layout="english"` 和独立的
`english_layout_state`，产品版本保持 `0.3.5`。旧 `uuid` 和 `readable` 布局继续按原规则读写，新包不会在打开工程、
创建 Run、重试或进入等待时静默升级旧工程布局。旧等待任务即使目录为空也保留原 handoff 路径。

新默认只用于新建工程。旧工程目录不能在资源管理器中直接改名；工程内可能已经保存工作、日志、交接及
Artifact 路径。整理与换盘继续遵守显式预览、确认、备份/保源、事务切换与可恢复失败规则，不自动迁移
操作者当前真实工程。

显式整理转换任务和处理轮次层级，历史 attempt 内部文件及旧收件子目录原样保留，避免猜测、改名或丢弃
未登记的用户来件。新处理轮次使用新的平铺收件结构；整理并不承诺重命名所有历史文件或删除旧端口子目录。

显式整理在切换引用前通过 SQLite 一致备份，在 `.zniku` 同目录保留
`<工程名>.before-storage-<UTC时间戳>.zniku`；重名时追加短序号，不覆盖已有备份。备份失败不得切换引用，
原媒体与已经复制的新位置文件继续保留；备份与原数据根共同构成旧候选回退所需的原始现场。

本次必须证明既有维护命令在新旧布局下不会误操作。若某种跨布局整理尚不支持，须明确拒绝，不能返回
成功、偷偷降回旧布局或在活动/等待任务期间改路径。旧候选不保证识别新布局；回退时需要原 `.zniku`
副本和原数据目录，而不是只保留媒体文件。

## 6. 路径与归档安全

- 新布局允许任务直接位于 `.data` 下，但受控副作用仍只落在绑定的独立 attempt，不允许把 `.data` 根、
  工程根、上游 Artifact 或用户原片当作工作目录或删除目标。
- 根/组件/文件校验继续拒绝上跳、绝对路径注入、Windows 保留名、大小写碰撞、链接/reparse、嵌套重叠
  attempt 和超长路径。缩短目录不等于保证所有外部软件支持任意 UNC 或长路径。
- Runtime 读取时验证持久定位，不能凭符合命名形状的邻居目录认领工作或产物。
- 本次 Windows 英文收件不依赖 NAS symlink、junction、hardlink，也不增加 SMB 特殊协议或自动重试；
  其他平台的既有 no-replace 发布机制不因此更换。
- 工程数据根缺失时维持只读维修入口，不创建空根、不回退系统盘。归属标记仍只是本工程定位，不是媒体
  digest 或完整归档证明。
- 历史 round、来件和已登记产物长期保留；完成、关闭、重跑、删除节点不自动删除。可重建目录索引继续
  不是 authority，归档仍应检查 `.data` 外的源文件和最终输出依赖。
- 英文布局的可选目录索引使用 `index.html`，按任务与 round 展示；旧布局继续使用 `文件目录.html`。
  生成索引不替换另一名称的用户文件、不创建媒体目录；内容继续使用中文说明，GUI 通过正式绑定定位索引。

## 7. 实施顺序与退出门槛

1. 版本化存储模型、英文命名提示与事务定位；新默认和旧布局兼容。
2. 收件定位统一：Runner、导入、目录扫描、批量导入、HostBridge 与路径验证消费同一规则。
3. 适配工程数据概览、显式整理/换盘、重新定位、目录索引和严格 Schema；GUI 只显示服务端结果。
4. 自动化回归及候选构建；记录实际通过项、跳过项和未证明范围，完成后才 commit/push。

必须覆盖：新工程不出现 `attempts/common/__N/R-A/port-hash` 正常收件层级；跨 Run/retry 的轮次、同名任务、
纯 reuse 无目录/媒体副本、别名不改路径、事务回滚、旧 UUID/readable waiting 提交、单输出平铺、章级多输出
平铺、大小写重名和危险 port、多候选拒绝猜测、保源与替换失败、新旧布局维护、归属/reparse/越界反例。

执行 Python 全量与专项测试、Ruff、mypy、Schema/corpus/版本一致性；涉及 Studio 时执行 typecheck、测试与
生产构建，使用纯合成项目完成正式服务端交接/重新打开/复用验证。门禁通过不等于真实 NAS/外部 AI 验收。

操作者待验包括：新短样本工程的真实目录可读性、文件管理器打开正确位置、直接交回与 UI 导入、章节批量
补件、一次重试和一次复用，以及在其指定 NAS 上的读写体验。本轮不自动执行真实媒体处理或迁移旧工程。
验收记录须逐项注明实际证据，不能沿用旧存储专项数字或把未执行检查填写为通过。

## 9. 新候选的验收方法

1. 等当前实际处理任务结束后，在旧候选中正常“退出应用”。不要终止仍在编码的进程，也不要只关闭标签页；
   同为 `0.3.5` 的候选共用单实例通道，旧服务未退出时可能仍然打开旧页面。
2. 从本轮独立候选目录启动，保留整个 one-folder 目录和 `_internal`；不要混合替换旧包中的个别文件。
3. 新建一个测试工程，验证 `source-repair/round-001/incoming`、`enhancement/A/round-001/incoming` 等
   实体路径。旧工程打开后仍保持旧路径，这是兼容保护，不是新布局未生效。
4. 分别使用直接放入 `incoming` 和 UI 文件选择交回合成或短样本产物；检查通过后仍需明确 Submit。
5. 验证一次重跑出现 `round-002`、旧轮次仍保留；纯复用不创建新轮次或媒体副本。
6. 真实旧工程整理必须在无活动或等待任务时显式预览、确认；备份文件及原数据均保留。不要手动重命名
   已绑定目录。真实 NAS 读写、长时间外部 AI 和归档体验仍由操作者验收。
