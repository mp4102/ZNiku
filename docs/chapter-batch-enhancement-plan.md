## 1. 采用的任务粒度

默认新流程先确定章节帧范围，再在各章内按已冻结的最长时长规则分叶。现有算法已经如此，
本次不重写分章数学，不先生成一套整章 FFV1 副本再二次分叶。

每章新增一个真正的批量人工增强 NodeInstance：一套增强参数、一份有序输入清单、设计时
确定的多个命名 VideoFile 输出，再通过普通有序 Edge 接本章 Merge。不是隐藏逐叶节点的 UI 群组，
不引入动态输出、全局 ArtifactSet、Map/Collect 或第二张 Graph。

N 个输入必须与本章 N 个输出一一对应。顺序、源坐标、章归属、帧数和媒体要求仍逐文件校验。
同章共享参数不表示已证明外部软件实际使用了该模型。只有整章全部通过，才登记全部输出并完成节点。

下游继续采用：章内增强合并 → 相邻增强章提供 FI 上下文 → 外部 FI → 精确裁边 →
顺序全片编码及原音轨封装。邻章依赖、仅全片末尾复制一帧的规则均不变。

## 2. 新旧兼容

旧 AV27、overlap、source-aligned 和 source-admitted 精确 NodeDefinition 保持原义。
新批量增强和需要接受新 producer 身份的下游使用独立 type_id，不冒充旧逐叶 producer，
也不放宽旧 parser 接受集合。既有工程、Run snapshot、waiting handoff 和媒体目标不改写。

新建默认流程使用章级批量模板。原有逐叶节点继续可用于高级编排，不在运行时偷偷拆解批量节点。
章级新定义由 Python 注册、命名、声明 Presentation 和校验，TypeScript 不计算分章、叶归属或文件匹配。

新 exact family 为 `zniku.source-admitted.enhancement-batch.<N>@0.3.5`，下游为
`zniku.source-admitted.chapter-batch.{merge,context,fi,crop,program,final}@0.3.5`。
输出 metadata 使用 `zniku.chapter.batch`；旧 source-admitted namespace 不伪装成新生产者。
章标签只保存在 StudioState 的可编辑实例名中，不改变 NodeInstance identity 或 reuse/stale。

## 3. 收件与正式完成分开

创作者操作为：

1. 选择本章任务，查看输入叶清单、共享要求及规范交付文件名。
2. 一次选择多个文件或一个输出目录；服务按规范名提出准确匹配，歧义必须人工选择。
3. 预览源文件、目标分叶和覆盖影响，明确确认后收件；外部原件默认复制并保留。
4. 可以分批补件、替换错误候选，显示“已收到 X / N”，不显示虚假的外部 AI 完成百分比。
5. 全部齐全时执行一次整章检查；通过后明确点击“提交本章并继续”。

提供本章专属收件目录的直接复制路径；发现只读取该 attempt 的有界单层目录，不递归扫描用户磁盘。
任意文件名可以手工映射，但不按目录顺序、文件大小或最新时间猜测。重复候选、同一来件重复分配、
未知目标、跨章/跨 Run/旧 attempt 绑定都不得自动认领。文件名仅帮助匹配，不证明内容归属。

单次选择最多 256 个文件，目录只检查首层最多 1024 项，不递归；整章最多 10,000 个固定输出，
更多于单次上限的来件分批提交。当前 Windows 批量路径不依赖硬链接；外部目录复制一次，
本 attempt 收件根确认后原位收纳，整章检查直接验证规范名来件，不另复制整章大文件。
映射盘的断连、权限和真实文件系统行为仍需在用户实际环境验收。

部分收件可跨应用重启保留，但不是部分 Artifact、编码 checkpoint 或节点内部 resume。
缺件或预检查错误保持 waiting_external；正式 Submit 仍执行现有完整重验，失败按 Core 整节点
failed/new attempt 处理。已有来件保留；重新交付需要明确操作，不自动把旧 attempt 部分文件视为成果。

导入或检查中取消/断连不能谎称所有行均成功，也不能回滚已完成行时误删媒体。必须报告或可重新观察
实际收件状态；未知响应先核对，不能自动重放副作用。覆盖逐项明确，原件和旧目标受到保护。

## 5. 验收条件

使用纯合成 fixture，不处理或修改真实用户媒体/工程，不自动操作外部 AI GUI。

- 三章共十五叶生成三个批量增强节点，不是十五个逐叶节点；一章一叶也使用同一章级交付体验。
- 修改一章共享参数只按正常 DAG 规则使该章及实际依赖下游失效，其他独立章节可复用。
- 有序输入、命名输出、源坐标和下游 producer 身份严格匹配；旧 exact 定义序列化和行为不变。
- 目录或多选一次交付；缺件、重复、错绑、未知字段、覆盖、迟到响应和中途变化均有回归。
- 部分交付不登记 Artifact、不触发 Merge；重开仍可观察来件；整章检查与 Submit 分别显式。
- 正式提交失败不会暗中降级为逐叶完成或自动续跑；错误保留来件和未覆盖旧目标。
- 合成增强/重叠 FI 全链保留源帧范围、总帧数、邻章上下文与音轨；不以合成结果冒充真实 Aion 验收。
- Python 全量测试、Ruff/format、类型检查、Schema/corpus 一致性、Studio 类型/测试/构建及相关浏览器门禁。

## 8. 候选测试方法

交付目录（相对于本工作树）：
`build/desktop-chapter-batch-20260916-rc2/dist/ZNIKU Studio/`。
双击其中 `ZNIKU Studio.exe`，必须保留完整目录及 `_internal`。
该包来源为 `1a9f3e4` 基点上的未提交工作树；版本仍为 `0.3.5`，不是该提交原样产物。

这是现有 `0.3.5` 的独立本地构建，不是自动升级或正式 Release。
启动前先在原 `0.3.5` 页面确认“退出应用”；两个包共用该版本的单实例通道，未退出可能重新打开旧包。
不要结束仍在执行的媒体任务，也不要只替换正在运行包内的某些文件。

1. 从新包新建测试工程，使用默认“ZNIKU 标准视频流程 · 0.3.5”。旧工程继续原 Graph，不自动转换。
2. 设置章节数与独立分叶时长。分析后确认工作流，应看到“A 章 · 批量增强 (N 份)”等章级任务。
   具体叶数由实际帧数和设置决定；“三章十五叶”是自动化专项，不是所有素材的固定结果。
3. 按章节打开输入叶清单，在外部软件使用本章同一增强设置；每叶保持原帧数、帧率和次序。
4. 点击“选择本章多个文件”或“选择本章文件目录”。也可把文件放入“本章收件目录”，再点击发现。
   规范名如 `Synthetic (2026).A.leaf-0001.enhancement.mov`；任意名可在预览中手工映射。
5. 核对映射并确认收件。可以先收 4/5、退出后重开再补第 5 份；这仍是等待状态，不会执行合并。
6. 收齐后点击“检查本章全部输出”。错误会指明问题分叶；替换该来件后重新检查。
7. 检查通过后点击“提交本章并继续”。系统才登记本章全部输出，并按原 DAG 进入合并及后续 FI。

真实待验：同一章多叶外部增强的文件选择与命名、分批补件/重开、真实专用磁盘或映射盘、长文件耗时，
以及外部 AI 的画面连续性与完整输出。自动化不证明外部工具实际使用了声明的模型，也不代替人工观感。

已确认的既有限制：Windows 上过深的工程/数据路径仍可能在创建收件目录或迁移时触发
`WinError 206`。本轮加长临时根的测试复现了 251/254 个 UTF-16 单位的目录失败；其中迁移用例
使用旧 UUID、旧单输出节点，同一限制在本次改动前已存在。对应三项在标准临时根重跑通过。
本次没有放宽路径保护或改写旧目录，建议使用较短的专用数据父目录；不宣称任意长路径可用。
