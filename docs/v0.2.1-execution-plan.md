## 1. 文档定位

本文是 ZNIKU Studio v0.2.1 的实施与验收计划，不修改 `graph-core-baseline.md` 已冻结的自由 DAG、普通
Run snapshot、节点级从头重跑、轻量媒体校验和本地可信工作站边界。

v0.2.1 解决的是 v0.2.0 最小实现进入操作者真实使用后暴露的三个缺口：

1. Studio 不能稳定展示正在执行或等待人工处理的 Run；
2. Runtime 虽保存 `progress`，但 automatic 节点没有真实进度来源；
3. 当前示例图只是形状近似 AVEnhanceFlow v2.7.0，媒体合同不足以用于该流程的真实验收。

AVEnhanceFlow v2.7.0 在 v0.2.1 中只能作为一份可选 workflow template 和专用节点包。不得把固定阶段顺序、
Task/State Runtime、Chapter/Leaf 全局代数或业务名称写入 Graph Core、Scheduler 或通用 Runtime。

## 2. 当前事实与问题基线

### 2.1 当前仓库与服务

- ZNIKU `main` 与 `origin/main` 同步，起点为 `48db558`；
- v0.2.0 已完成自由 Graph、Project Store、Runtime、Project Service、Studio 和首批通用媒体节点；
- Phase 5 的短媒体 smoke 证明了通用 8 节点 DAG、Split/Merge、发布和结果复用，不证明
  AVEnhanceFlow v2.7.0 的专用媒体合同；
- 当前浏览器联调使用 Vite `127.0.0.1:5173` 和 Project Service `127.0.0.1:18765`。

### 2.2 当前运行可见性缺陷

一次本机只读诊断确认了问题，但旧 Project snapshot、路径、Run ID 与真实节点数量都不写入 Git。Phase 0 只用
以下纯合成三 Run 形状固定回归：

| Run | 目标 | 当前状态 |
| --- | --- | --- |
| 较早 Source Run | Run to Source | completed |
| 中间整图 Run | Run all | Source completed、manual waiting_external、sink pending |
| 最新 Source Run | Run to Source | completed；`active_run_id` 指向它 |

Project Service 的 `active_run_id` 会被最后一次局部操作覆盖，Studio 又把它当成唯一显示 Run，因此整图 Run
仍在等待 MR 时，GUI 却展示局部 Source Run 的 `completed`。当前实现还存在以下问题：

- 只有 `active_operation != null` 时每 750 ms 轮询；
- worker 到达 `waiting_external` 后返回并清空 `active_operation`，轮询停止；
- Run 历史、节点 overlay、Inspector、日志和 Submit 都只绑定一个 Run；
- `waiting_external` 存在时仍可无提示创建新的 Run；
- Submit 前没有只读文件就绪预检，误点会使 attempt 进入失败终态；
- status 每次返回全部历史 Run、Artifact 和日志尾，长期高频轮询会不断增重。

### 2.3 当前进度缺陷

`NodeRun.progress`、SQLite 字段、`RuntimeRepository.update_progress()` 和 Studio 百分比组件已经存在，但正式
Runtime 没有调用 `update_progress()`。automatic 节点当前表现为：

```text
pending → running(0%) → 同步 subprocess.run → completed(100%) / failed
```

因此 v0.2.0 只有状态变化，没有真实帧级或时长级进度。manual_external 节点也不具备 Jasna/Topaz 内部进度
来源，不能伪造百分比。

### 2.4 当前 AVEnhanceFlow 映射缺陷

当前 11 节点图与 v2.7.0 的形状相似，但不能称为兼容或验收链：

- Split 按 segment 循环启动多个 FFmpeg；v2.7.0 要求每个物理 Source 一个连续 producer；
- Enhancement 缺少 ProRes 422 HQ、`yuv422p10le`、整数 scale、signal 和 stage-wide model 一致性；
- FI 当前要求 `N→2N`；v2.7.0 要求逐章 `N→2N-1`；
- generic EncodeVideo 不执行逐章补尾、canonical 双倍帧率 PTS、章首 IDR 和一个连续 ProgramEncode；
- generic MuxMedia 对每个输入只映射第一路 `a:0`，不能保证保留原始全部音轨与顺序；
- manual external 的默认 `.mkv` 目标不适合 Enhancement/FI 常见的 ProRes `.mov`；
- Enhancement/FI 当前强制填写 `model_version`，而 v2.7.0 允许 model version 缺失；
- 现有工程没有明确区分 ChapterPlan 与 LeafPlan。

## 3. v0.2.1 目标与完成定义

v0.2.1 只有同时满足以下条件才可交给操作者进行真实短片验收：

1. Studio 始终明确显示用户当前查看的 Run，不被后续局部 Run 静默替换；
2. 非终态 Run、`waiting_external`、失败节点、日志、输入与目标路径实时可见；
3. automatic 媒体节点提供可信、单调、持久化的进度；
4. manual_external 没有可信外部进度时只显示等待和文件就绪状态；
5. Run all 不会因误触产生无法识别的重复 Run；
6. handoff 输出缺失、为空或 probe 不通过时，预检不改变 NodeRun 状态；
7. 提供由 Python authority 生成的 AVEnhanceFlow v2.7.0 模板；
8. v2.7.0 专用节点满足 Split、Enhancement、FI、ProgramEncode 和 FinalMux 的关键媒体合同；
9. 通用 v0.2.0 Graph Core 与媒体节点继续可用，旧 Project 不被自动改写；
10. 新建的干净短片工程可以从 Run all 经过人工 Submit、自动编码和最终发布完整闭环；
11. Python、Studio、Schema、类型检查、代码质量、构建和短媒体自动门禁全部通过；
12. 真实媒体、运行目录、handoff、日志与最终输出均不进入 Git。

## 5. 冻结的实施决策

### 5.1 Run 身份与展示身份分离

- `active_operation` 只表示 Project Service 当前后台 command；
- `active_run_id` 只表示最近一次 command 绑定的 Run，不再作为 Studio 唯一显示权威；
- Studio 新增本地 `viewRunId`，由操作者显式选择；
- 新 command 成功创建 Run 时自动切换到该 Run；
- 用户手动选择后，普通 refresh 不得改变选择；
- 页面重载时优先选择最新 actionable Run，其次选择最新 Run；
- actionable 精确定义为 Run state 是 `pending` 或 `running`；尚未物化 attempt 的 queued pending Run 也可选择。

### 5.2 第一版采用单飞轮询

v0.2.1 首先采用有界 single-flight polling，不立即引入 SSE/WebSocket：

- 上一次请求结束后才安排下一次，不使用可重叠的 `setInterval`；
- `active_operation` 存在或任一 RunSummary actionable 时继续 status 轮询；所选 Run detail 是独立
  channel，只由 `viewRunId` 对应 Run 的状态决定是否定时刷新；
- worker 结束时强制执行一次 final refresh；
- 请求失败时指数退避，保留最后一次可信状态；
- Studio 为每个资源 channel 维护本地 `projectGeneration/requestSequence`，旧 generation 或旧 sequence 的响应
  不得覆盖新状态；wire 不新增服务端 revision；
- running 期间目标间隔 750 ms，waiting/pending 期间 1.5 秒；全部 Run 终态时仍以 5 秒
  低频检查 status，以发现其他页面启动的新 Run；
- SSE 只在轮询负载或事件延迟经测试证明不满足要求时进入后续版本。

### 5.3 进度必须可信

- automatic 节点只有在 executor 提供测量值时显示百分比；
- 进度只能单调递增，Runtime 继续使用已有的 `0.0..1.0` 合同；
- 更新按时间或最小增量限频，避免每帧写 SQLite；
- completed 必须为 `1.0`，failed 保留最后可信进度；
- reuse 节点直接显示 `completed / reused`，不模拟执行过程；
- manual_external 只显示 `Waiting external`、等待时长、文件就绪和验证状态；
- Run 汇总同时显示“完成节点数/闭包节点数”和当前 automatic 节点百分比，不把两者混成一个假精度数值。

### 5.4 AVEnhanceFlow 只作为节点包与模板

专用节点固定使用独立 type namespace `zniku.avenhance.v27.*`。它们仍是普通 NodeDefinition，依赖现有
Graph、Scheduler、NodeRunner、Artifact 和 rerun/reuse 语义。Python template builder 先生成 preparation Graph，
再基于 admitted Artifact 扩展普通 NodeInstance、Edge、exact definition snapshot 和参数；Studio 不复制媒体合同。

模板兼容范围是“v2.7.0 流程形状与关键媒体输出合同”，不是 AVEnhanceFlow Task/State 文件互操作。通用
`zniku.media.*` 节点继续保留，不被硬化为 AVEnhanceFlow 专用节点。

### 5.5 当前错误工程只保留诊断价值

既有本机诊断 Project 不继续 Submit、不删除、不自动迁移。v0.2.1 验收使用新的独立工程文件，避免三个既有
Run、错误 FI 合同和 generic Encode/Mux 结果污染结论；具体本机路径不得写入 Git。

## 6. 目标节点图

模板在 authoring time 明确 ChapterPlan 与 LeafPlan，然后生成普通静态 Graph：

```text
SourceProgram(s).video ────────────→ MR? ──→ AtomicSplit → Enhancement/Merge/FI → ProgramEncode
SourceProgram(s).source_media ─ordered_many→ SourceAdmission.sources
                  └────ordered_many─────────────────────────────────────→ FinalMux.sources
SourceAdmission.gate ─┬─→ MR?.gate
                       ├─→ AtomicSplit.gate
                       └─→ FinalMux.gate
ProgramEncode.video ─────────────────────────────────────────────→ FinalMux.video → OutputFile
```

所有模式先运行只含 SourceProgram、SourceAdmission 和 optional MR 的 preparation Graph；Python 选择
effective-video Artifact binding 后派生 Chapter/Leaf 并追加后半图。第二个 Run 复用 completed preparation
节点。单章工程只生成一个 Merge/FI；
每章可以有一个或多个 Enhancement leaf。ProgramEncode 接受按 chapter ordinal 连接的
`ordered_many<VideoFile>`。第一 Run 建立 SourceProgram video/source_media Artifacts、admission gate Artifact 和可选
MR output Artifact；Python 不新造“admitted video”类型，而是在 expand 时选择 MR output（external）或已有
SourceProgram.video（off）作为 effective-video binding。FinalMux 直接消费原始 Source MediaFile，而不是从 AI
视频支路取得音频。

### Phase 3：AVEnhanceFlow v2.7.0 专用节点包

目标：实现可以由自由 Graph 组合的 v2.7.0 关键媒体节点，不引入第二套 Runtime。

建议模块：

```text
src/zniku/avenhance_v27/
├─ definitions.py
├─ adapters.py
├─ validators.py
├─ profiles.py
├─ planner.py
└─ template.py
```

通用 Runner plumbing 同期实现，但不得按 `zniku.avenhance` type ID 分支：

- `RunnerInput` 只读携带完整 Artifact producer binding、`frame_range`、`media_info`、size 与 mtime；
- `PythonAdapterResult` 可按 output port 上报严格 `producer_metadata`；validator 闭合后只向
  `Artifact.media_info["zniku.avenhance.v27"]` 写规范 metadata，不能覆盖 probe 或持久 raw producer object；
- `NodeDefinition.executor` 可声明受控 per-port attempt 内相对 `output_paths`，不增加 NodeDefinition
  顶层字段；Service 泛化传入现有 `NodeExecutionRequest.output_paths`，Runner
  继续拒绝 absolute、`..`、重复/未知 port 和 containment escape；
- v2.7 definitions 因而可以声明 MR `.mkv`、Enhancement/FI/Merge `.mov`、Program `.mp4` 与 Final `.mkv`，
  无需把后缀塞入用户参数或 Runtime 业务判断。

#### 3.1 SourceProgram

- 输入参数是明确的绝对 Source 路径；
- 输出 `video: VideoFile` 与 `source_media: MediaFile`，都只读引用原文件；
- 验收恰好一条视频，允许任意音频；
- 拒绝 subtitle/attachment/data/unknown 和内置 chapters；
- 建立 canonical rational FPS、geometry、signal 和 N；
- 只保存轻量 summary，不计算媒体 SHA；
- `source_media` 是 FinalMux 原始音轨唯一来源。

#### 3.2 SourceAdmission

- `sources: ordered_many<MediaFile> → gate: DataFile`；
- 在任何 MR handoff、Split 或 FinalMux 前完成全部 Source 的 fresh runtime admission；
- pre-chaptered 在此核对跨 Source logical audio signature；
- admission 只是普通节点 DataFile/result summary，不是 Evidence、receipt、hash 或第二套 authority；
- gate output 作为 MR、Split 与 FinalMux 的 required 普通输入，不能依赖 Scheduler 偶然顺序。

#### 3.3 MosaicRestoration external

- `VideoFile → VideoFile`；
- 目标后缀 `.mkv`；
- `N→N`；
- FPS、geometry、SAR 与 signal 不变；
- actual model name/version 必填；
- 可选节点，不存在时 Source video 直接进入 Split。

#### 3.4 AtomicSplit

- authoring time 已知全部 leaf output ports；
- 每物理 Source 只启动一个连续 FFmpeg producer；
- 输出固定 1080p FFV1 Level 3、`yuv420p10le`、BT.709 SDR；
- frame range 连续、唯一、有序并完整覆盖；
- 任一输出失败时整个 attempt 失败，部分输出不登记；
- 自定义端口 shape 使用稳定 type identity，不在运行时动态增加端口；
- 不恢复 ArtifactSet、Map/Collect 或动态成员语义。

#### 3.5 Enhancement external

- 每个 leaf 一个普通 NodeInstance；
- 目标后缀 `.mov`；
- 恰好一条 ProRes 422 HQ `yuv422p10le` video；
- `N→N`、FPS 不变；
- 允许输入工具产生的附带流，但下游 Merge 只消费 video；
- actual model name 必填、version 可选；
- scale `k` 必须为正整数，`k>1` 显式声明；
- template preflight 检查全节目 stage model、version presence 和 geometry 一致。

#### 3.6 MergeVideo v2.7

- 每章一个节点；
- `ordered_many<VideoFile> → VideoFile`；
- 只消费按 leaf ordinal 排列的视频；
- 执行 video-only concat/remux，不携带 AI 支路音频；
- 输出 ProRes/geometry/FPS 与输入闭合；
- 输出帧数等于 leaf 总和。

#### 3.7 FrameInterpolation external

- 每章一个节点；
- 目标后缀 `.mov`；
- video-only ProRes 422 HQ `yuv422p10le`；
- geometry 不变；
- frame rate 与 source×2 在 v2.7 容差内等价；
- 精确 `N→2N-1`；
- actual model name 必填、version 可选；
- template preflight 检查全节目 model/version/geometry 一致。

#### 3.8 ProgramEncode

- 全节目只有一个节点；
- 输入为按 chapter ordinal 排列的 `ordered_many<VideoFile>`；
- 每章 FI 末尾补一帧，从 `2N-1` 闭合到 `2N`；
- 全部章节只启动一个连续 FFmpeg encode；
- 按 source exact FPS×2 重建 canonical PTS/time base；
- 保留章首 forced IDR；
- 输出 HEVC Main10、BT.709 SDR、`hvc1` 与 exact track timescale；
- 不做 spatial rescale；
- CPU/GPU 选择固定为 ZNIKU 节点参数，不增加 attempt override，也不写入 Graph Core；
- capability probe 失败时不得自动 fallback；
- 中断或失败后从头重跑 ProgramEncode，已完成 FI 保持复用。

#### 3.9 FinalMux

- 输入 `video: VideoFile`、`sources: ordered_many<MediaFile>` 与 required `gate: DataFile`；
- video 只来自 ProgramEncode；
- audio 只来自原始 SourceProgram 的 `source_media`；
- 按 source ordinal 映射每个 Source 的全部原始音轨；
- 保留音轨数量、顺序和必要 metadata/disposition；
- 输出恰好一个预期视频与全部预期音轨；
- 最终名称与 overwrite 行为由显式参数决定；
- v2.7 canonical Jellyfin naming 可作为模板默认和 validator，不成为 Core 唯一 Final 规则；
- ZBaton 作为后续可选 Export，不回滚已完成 Final。

测试任务：

## 9. 风险与控制

### 9.1 高频进度写入

风险：FFmpeg 每帧上报导致 SQLite 写放大。

控制：progress callback 在 Runtime 层按最小时间和最小增量合并；最终状态强制 flush。

### 9.2 status 响应持续增大

风险：全历史 Run、Artifact 和日志随轮询反复传输。

控制：拆分 RunSummary、selected Run detail 和 log tail；waiting 采用低频轮询。

### 9.3 模板污染 Core

风险：为 AVEnhanceFlow 增加 Scheduler 业务分支或固定 scope。

控制：模板只生成普通 NodeInstance/Edge；专用媒体规则只在节点 adapter/validator 和 template preflight。

### 9.4 与 AVEnhanceFlow 形成第二套状态

风险：直接调用完整 `avenhance` task runtime，产生双重状态 authority。

控制：不读取或写入 AVEnhanceFlow task/state；只参考冻结媒体合同并实现 ZNIKU 节点。

### 9.5 外部工具无法提供真实百分比

风险：操作者误以为 ZNIKU 能监控 Jasna/Topaz 内部工作。

控制：manual_external 明确显示“外部处理中/等待提交”，只有文件 readiness；未来专用集成必须另行设计。

### 9.6 Patch 版本兼容

风险：新增 wire 字段或 exact NodeDefinition 使 0.2.0 Project 无法打开。

控制：旧 Project definitions 随 snapshot 读取；新增字段优先放新 endpoint/可选 projection；v0.2.1 不执行
Project migration，不改写历史。若未来版本确需 migration，必须另行设计、批准与验证。
