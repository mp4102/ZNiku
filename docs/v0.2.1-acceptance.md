## 3. 生产版 GUI 验证

使用 `npm run build` 的产物及真实 loopback Project Service，不以开发服务器或 TypeScript mock 代替验收。
只在新建的独立验收 Project 操作，旧诊断 Project 不打开、不修改、不 Submit、不迁移。

验收顺序：

1. Templates → Preparation：只读 preview，然后 no-overwrite 创建 Project。
2. Run all 完成 Source/Admission；明确选择该 completed preparation Run。
3. Templates → Expand：服务器派生 Chapter/Leaf、exact ranges 和 canonical target。
4. 第二 Run 复用 preparation 节点，显示真实 Split 测量进度与定向日志。
5. 人工队列显示原 Run 的输入、唯一目标、模型声明及媒体合同；缺文件不能 Submit。
6. 合成工程中通过完整 readiness 和显式 Submit 验证同一 Run 自动继续、最终输出与后续 reuse。
7. 重载、切换历史 Run 后，actionable Run、当前 handoff 和日志仍可正确定位。
8. 检查浏览器 console errors；任何失败必须记录，不能以页面能打开代替验证。

本次实际观察：

- 真实短片首次由 GUI 创建并展开；Source/Admission 在第二 Run 复用，Split 显示测量帧数与百分比后完成，
  初始两个 Enhancement handoff 保持 waiting，未伪造外部产物。
- 随后操作者明确改用 10 分钟分叶：GUI 先 Abandon 旧 waiting Run、保留历史与文件，再从原 completed
  preparation Run 重新 preview/expand。新图保持单章，只有一个 leaf；新 Run 复用 Source/Admission，
  Split 创建新 Artifact，唯一 Enhancement 使用新 handoff/target，等待实际外部产物。
- 操作者进一步澄清需要精确帧切章，单改分叶时长并未满足原意；当前已保留 10 分钟分叶并指定
  `exact_frames` 章界。经正式 preview/expand 和新 Run，Split 已完成为两章各一 leaf；两个
  Enhancement 均使用全新 handoff/target，旧单章 Run 已 cancelled，历史和文件不删除。
- 操作者提供实际外部增强产物后，旧单倍尺寸合同的完整预检明确拒绝 geometry 不匹配，没有发送
  Submit。经操作者批准保留双倍输出，再次通过 server-side preview/expand 创建新 Run；Source、
  Admission、Split 全部复用，相同两份完整产物复制到新 handoff 后，分别经生产 GUI 完整预检与正式

## 4. 真实短片与人工交接

本机 Project、Run/Artifact ID、路径、媒体属性、日志与 handoff 操作单只保存在仓库外的本机验收目录；
不提交 Git。Source 只读引用，不剪短、不规范化、不覆盖。正式 SourceProgram fresh admission 决定 N/FPS；
最初按计划使用单章与 `leaf_duration_minutes=1`；随后依照操作者明确要求改为
`leaf_duration_minutes=10`，随后按操作者澄清的精确帧边界分为两章。所有 ranges 由 Python 派生，不能通过丢帧、补帧或
静默合并尾叶改变分叶结果；本次只改当前验收工程参数，不修改模板或 Runtime 合同。

### 第一轮：MR off

操作者使用实际 Starlight Precise 处理每个 leaf，按 GUI 合同导出 ProRes 422 HQ `.mov`，关闭外部导出后再
完整预检并 Submit。全部 leaf 通过后，同一 Run 自动 Merge 并产生 Aion FI handoff。

当前两份操作者提供的完整 Enhancement 与两章 FI 均已通过正式节点 validator 和 Submit，两个 Merge 已完成；
本轮按操作者批准保留整数双倍输出，没有缩回单倍、改写旧 Run 合同或绕过校验。实际尺寸、N/FPS、
Artifact 与交接路径仅记在仓库外的本机操作单；这不证明实际模型身份或主观画质。

该 MR-off Run 已通过真实 Program、原音轨 FinalMux 与 OutputFile 发布；GUI 显示全部最新节点完成，
没有 waiting/failed，浏览器 console errors 为零。SAR 失败历史与原文件均保留，失败 attempt 未登记 Artifact。
发布后的独立完整帧计数与 Program 合同一致，geometry/Main10/SAR/完整 signal、原音轨 signature 和
容器布局通过核对；Matroska 帧周期表示误差仍在既定容差内。真实 Source 大小与修改时间保持不变。

FI 必须是 video-only ProRes 422 HQ，精确 `2N-1`；不能将 `2N` 输出自动裁一帧来冒充外部工具兼容。
FI Submit 成功后，同一 Run 自动完成逐章补尾、一次连续 ProgramEncode、原音轨 FinalMux 和不覆盖发布。

该轮是计划推荐但不阻断 Phase 5 的扩展兼容性覆盖，当前未执行。执行时应新建独立 Project，并先填写实际

### 最终验收

- Source 的路径、大小和修改时间保持不变；本阶段不引入强制 payload hash。
- 每个外部输出均通过实际节点 validator；未完成导出、缺失/空文件和错误合同不得登记 Artifact。
- Program/Final 为 HEVC Main10、exact source FPS × 2，Program 总帧数为 source N × 2。
- 全部原始音轨数量、顺序、必要 metadata/disposition 保留，没有 AI 支路音频或意外字幕/附件。
- Output 不默认覆盖；失败使用新 attempt，completed 上游可复用。
- 真实输出的主观画质由操作者检查，不能由技术合同替代。

## 5. 本阶段发现与修复

1. **人工交付信息不足**：Run detail 新增只读 `handoff_contracts`，Python 从原 Run snapshot 与已绑定输入
   Artifact 生成 N/FPS/geometry/signal/codec/容器/模型声明；不增加 Runtime authority。Studio 同时提供已
   登记 Source media summary。
2. **预检错误难定位**：显示服务端具体错误，不把错误压缩为 `probe_failed`；上次完整预检失败独立绑定
   Run/NodeRun/handoff，不能被普通存在性轮询抹掉，也不能串到新 attempt。
3. **人工等待计时不准**：从 `started_at` 而非排队时的 `created_at` 起算，避免把上游处理算成人工等待。
4. **Final fractional FPS 误报**：只对 Matroska observed header 的帧周期允许不超过 1 ns 的表示误差；三个
   rate 字段均检查，canonical FPS 仍来自 Program；Program exact/time base、FI 和帧数均未放宽。正反例
   覆盖量化边界、单字段冲突及错误 geometry。
5. **依赖审计**：只把间接 `fast-uri` 从 3.1.5 更新至 3.1.7，不升级 Vite 或产品版本。此前锁定版本处于
   [维护者公告的受影响范围](https://github.com/fastify/fast-uri/security/advisories/GHSA-f65p-4m7j-42xc)，
   更新后 audit 为零；这不是对应用实际可被 SSRF 利用的声明。
6. **外部 FI 缺 SAR 导致 Program 失败**：外部 validator 允许缺标签并按 square 解析，而 Program 必须
   输出显式完整标签。原 producer 继承了外部缺失 SAR；修复为每章在 concat 前设置 `setsar=1/1`，
   CPU/GPU 共用，不改变 geometry、FPS 或帧数，不放宽 Program validator。合成 E2E 改为一章缺 SAR、
   一章显式 `1:1`，已确认修复前失败、修复后完整闭环通过；Program 缺 SAR 的反例仍被拒绝。

## 7. 已知性能限制

本轮真实工程的 OutputFile 复制可持续推进，但耗时明显高于小型合成工程。只读代码复核确认：每 1 MiB
进度回调在限频判断前同步执行完整 Run 校验；其中还包含 Project 全历史 attempt 目录的两两重叠检查。
需要持久化的 sample 会重复完整读取与审计，部分工作位于写事务内。FFmpeg stdout 消费也同步调用此链，
因此存在复制与日志读取被回调阻塞的风险。

这是已确认的热路径复杂度问题，但尚未量化本次耗时中各因素的占比；本次 SAR 修复未顺带更改 Runtime
校验边界。后续应以合成多历史 Run fixture 做 profiling 和独立回归，再优化该路径，不通过关闭校验或伪造
完成状态掩盖延迟。
