把新建普通视频流程收敛为一套源媒体规则：采用 AVEnhanceFlow package 2.7.0 实际 Source
准入；通过就继续分章/分叶，不通过时允许用户在外部修复并显式导入候选，候选重新走同一准入。
内置不执行时钟修复、重定时、色彩修复或自动转码；不增加 strict/color/work 等并列处理模式。

本次是媒体节点与 Studio 集成修订，不是 Core 重构。唯一上位权威仍为
[Graph Core](architecture/graph-core-baseline.md)，展示遵守

[现有业务合同](architecture/chapter-overlap-fi-baseline.md)。本备忘录不覆盖这些权威。

## 3. 源准入与外部修复边界

以本机 AVEnhanceFlow 2.7.0 源码和 skill 合同交叉核对以下规则，并用合成 fixture 固化：

- 视频/音轨结构、无内置章节、16:9、工作域与明显不支持的 HDR/隔行/旋转/SAR 条件。
- `avg_frame_rate` 与 `r_frame_rate` 的等价容差及 canonical FPS，而非字符串或 Fraction 完全相等。
- 每次 Source 准入一次完整 packet timeline，取得 packet count 与 cadence；DTS 不足时才走
  decoded presentation fallback。不额外强制 raw PTS 等于 best-effort PTS。
- 沿用 AV2.7 的 confidence、覆盖率、节奏与 N/FPS/时长闭合规则，不自行扩大为全片内容证明。
- 缺失/unspecified 色彩标签按 AV2.7 的 BT.709 SDR limited 工作解释并警告；明确冲突继续拒绝。
- 有界、可取消的真实分析；状态查询不重复扫描。警告不伪装失败，也不要求为了警告额外确认。

外部修复与可选马赛克修复是两回事。源无法准入时显示具体问题及“选择修复后的视频”；
文件出现不自动提交。候选通过同一源准入后，经显式动作作为新的处理参考，N/FPS 和音轨来自候选，
不宣称与原片内容等价。重新分析、重新规划，不沿用原片陈旧的范围、结果或音轨绑定。
VideoSourceRepair 可以是操作者选择的外部工具，但 ZNIKU 不信任报告替代媒体检查，也不承诺它能修复所有失败。

## 4. 实施顺序与交付物

1. **基点修复**：定位 v0.3.3 远端 Python 9 项及生产浏览器5项失败，区分实际缺陷、工具差异与
   测试假设。先提交可独立验证的小修复；不删除测试、放宽帧守恒或以跳过掩盖失败。
2. **单一准入**：新 exact Source 节点/局部适配、AV2.7 规则对照与测试；尽量复用原有下游。
   新建流程默认使用新准入，旧 exact 路径仍保持原义。对后续 validator 的再阻断必须做全链检查。
3. **外部候选与 UI**：复用原生 picker、明确确认及已有节点级运行机制。普通路径只显示检查进度、
   结果/警告和下一步；失败给外部修复入口。避免增加业务专属 Runtime 状态或复杂恢复协议。
4. **集成验收**：测试候选成功、失败、取消、迟到响应、保存重开、reuse/stale、MR on/off、
   三种分章、外部增强/FI 合成完整链及旧工程回归。独立审查 Core diff。
5. **交付**：版本与文档一致，生成隔离 Windows 候选包，运行全部相关门禁，commit/push 并检查
   远端 CI。未通过门禁必须明确报告，不将本地通过当作远端通过，不将合成测试当作真实 AI 验收。
