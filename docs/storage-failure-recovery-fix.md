## 1. 问题与证据边界

一次真实工程处理在外部步骤全部完成后发生存储访问错误；后续自动节点已经停止，数据库却仍保留
`running`。再次打开工程的界面只给出泛化提示，不能区分工程缺失、存储不可写和服务异常。

只读检查表明工程数据库可读取且完整性检查通过，已登记成果仍存在。新建独占诊断文件则得到
`ENOSPC`，而操作系统容量查询仍报告剩余空间；用户清理存储后，同目录 SQLite 创建、提交、回滚均恢复。
这证明了诊断时存储不可写，不足以证明最初中断的每一层异常，也不等于数据库损坏。

真实工程、备份、路径、日志和媒体不进入仓库。现场恢复前使用只读源连接进行 SQLite 一致备份，
不直接复制正在变动的主文件，不删除数据库 journal/WAL 文件，不修改状态冒充完成。

## 2. 修复目标

1. SQLite 连接与访问异常返回结构化服务错误，保留原始原因，不因未捕获异常退化为 `Failed to fetch`。
2. 受控处理停止后，存储已可写时通过正式状态迁移记录失败；仍不可写时明确要求恢复存储后重新打开，
   不谎报处理仍在推进或失败已成功保存。
3. 未确认子进程退出时保持保守阻断，不能开放与旧进程并发的重跑。
4. 后台失败不被无关命令或失败的恢复尝试静默清除；错误信息不重复堆叠同一错误码。
5. 最近工程打开失败保留具体原因；保存、读取、运行存储问题明确说明保留内容与下一步，不宣称未保存的
   编辑已落盘，不仅凭通用 SQLite 打开失败就判断磁盘已满。

## 3. 真实恢复流程

1. 确认没有对应处理进程，备份 `.zniku`，核对已登记输出仍存在。
2. 使用全新诊断文件验证工程目录可写；测试文件不占用用户文件名，不试写正式工程。
3. 通过正式打开入口运行既有中断恢复：遗留 `running` → `failed(reason=interrupted)`。
4. 预览从失败节点重跑的影响，确认只有该节点及下游会创建新 attempt；已完成且有效的上游继续复用。
5. 从头执行新 attempt，保留旧半成品，不采纳部分中间文件、不恢复字节或帧偏移。
6. 新产物仍须进程成功退出、文件存在非空、媒体 probe 与原节点 validator 通过，才登记为 Artifact。

## 5. 保留的边界

- 本补丁不能修复 NAS 本身的空间、配额、连接或权限；恢复可写仍是操作者的前置操作。
- 无法确认 producer 退出时的阻断保存在当前服务进程中，不是跨实例锁。退出或重启应用前仍须
  确认旧处理进程已停止；不扩展为分布式 lease 或多实例调度。
- 不自动迁移工程数据库、不自动重试或删除旧半成品，不改变媒体合同、Graph 或成果复用语义。
