## 1. 实际实现

- 产品版本统一为 0.3.4，独立 `codex/v0.3.4` 工作区；原开发区、旧候选、用户服务和真实工程不修改。
- `zniku.source_preparation` 新增只读实体 Source、完整 Diagnostics、T1 工作副本、
  三种封装的 external repair 与输入型 Admission，共 7 个 exact definitions。
- `zniku.prepared_source` 新增工作参考绑定的 8 个下游角色和 3 种 MR 封装定义。
  复用旧分章/FI 数学与媒体 helper，不修改旧 0.2.1、0.3.2、0.3.3 exact 合同。
- original/reference/effective/audio 分离；准备副本不意味着开启 MR，Final 不取 MR 或 FI 的音频。
- T1 与外部保内容修复在各自节点内部完成完整帧序/像素、音轨样本、属性及时间关系检查，再登记媒体。
  原件视频时钟异常不妨碍独立观察和使用合格原音轨；没有音轨的行为须显式声明。
- 新 Project Service wire 0.3.4 负责检查视图、路线选择、停止与同图展开；保留 session/CAS、snapshot、
  当前输入和 stale 检查。没有隐藏图、Compiler 或新的 Runtime 状态机。
- Studio 保留四项建项输入，显示问题、实际阶段/速度/耗时、来源及可选处理；外部导入沿用同一任务助手，
  可停止完整验证、保留候选并重新检查。未知总量不显示假百分比。
- 使用既有 `.data` 持久可读布局，副本名为 `标题.source-prepared.mkv` 或
  `标题.source-repaired.<实际封装>`；正常源只读引用，不复制。
- Windows 包增加可选 MKVToolNix 及原许可核对；若策略晋级则必须随包具备工具。
  包审计验证实际源码、PYZ、静态资源、工具字节与能力清单，不只信任 BUILD-INFO 自报。

## 2. 独立审查修复

| 问题 | 修复及回归依据 |
| --- | --- |
| 自定义节点借用正式 validator 铸造 metadata | adapter/validator 全部匹配完整 exact definition，含 executor、Schema 和端口 |
| 原始 stdout EOF 后取消/超时预算丢失 | EOF 后等待同样检查取消及原截止时间，真实短子进程回归 |
| 准入 gate 或外部目标率与直接输入不一致 | 核对策略/原件身份、相对音频坐标、载体和诊断目标率 |
| H.264 明确 fixed VUI 与目标率矛盾 | 有界初始 SPS 观察并拒绝明确冲突；报告不宣称全片 SPS 恒定 |
| 外部 readiness 与换工程竞态 | 锁内核对捕获 runtime/session，长验证在锁外；旧 Run 不能停止新操作 |
| 改节点 ID、加入其他节点或展开图后，模板门禁拦住检查进度/停止 | 独立 operation-view/cancel 按实际活动 Run/attempt 及完整 exact definition 校验；不再依赖模板名字或图形状，向导选择/展开门禁不变 |
| 新旧 Schema 共存导致缓存反复失效 | 原有有界语法缓存 32→128；不缓存参数结论，不放宽验证 |
| Windows 刷新时单个模块连接被拒绝而空白 | 静态模块失败路径及服务仍存活证据；desktop 待 accept 队列 5→32，16 连接真实突发回归红→绿 |
| OS 随机分配浏览器禁用端口，入口无法打开 | 实际复现 4045 被浏览器拒绝；按 Fetch Standard 闭合表至多重新分配 32 次，只释放本次未发布 listener |

刷新修复不是浏览器重试或延长超时；仅增加本机有界连接等待队列，请求授权及并发执行门禁不变。

## 5. 尚未关闭的阶段门禁

T1 实现及合成试验不代替真实代表和冻结后留出。
本轮重新读取既有匿名普查报告，原拟选的两个开发与两个留出样本都缺少完整色彩声明；
47 个既有头检记录中只有 1 个具备当前白名单全部色彩字段，它是既有正常类别，不构成 T1 正例对照组。
这是旧报告的复核，不是再次全片读取后的新结论，也不说明这些视频损坏。

因此，先前拟定的四文件真实写入安排不能直接作为当前策略通过集执行；本轮未写真实候选。
不能只补 BT.709 标签或放宽未知属性门禁来取得测试通过。政策审阅时列出的两条选择为：

1. 明确满足已冻结属性白名单的真实开发代表及独立留出，并单独确认原件、目标率/策略和新输出目录；或
2. 单独审阅“缺失色彩声明”的处理政策及适用证据，再修订下位合同和反例；不静默猜测源色彩。

用户现已批准第 2 条，当前按第 7 节的新合同实施。政策批准不等于这些样本已通过完整分层检查，
也不等于替其采用工作解释或授权生成真实修复候选。

取得可用样本及写授权后，串行执行完整诊断、候选、视频/音频比较和真实下游 Admission，
记录每阶段耗时、大小、CPU/内存、读取范围及未测指标，通过后才晋级 T1。
若没有任何策略通过，Phase 2 继续不标完成；Phase 4 三条可用产品路线也不能提前关闭。
Phase 5 真实外部增强/FI、用户成品检查及正式发布仍不在本轮完成声明内。

## 7. 已批准工作色彩政策：0.3.4-color.1 增量

### 7.1 当前实现

- 产品仍为 `0.3.4`，新增 18 个 exact `0.3.4-color.1` 节点；旧 18 个 `0.3.4` 定义的完整形状保留。
  `source_color` / `prepared_color`、wire/profile、Gate 与 metadata namespace 分离。
- 容器原始声明、全部 H.264 SPS/SEI、完整解码帧分别观察；未知解析不能成为“缺失”。
  逐字段保存原始值、规范推导、来源；冲突、全片变化、HDR/ICC/不支持扩展均失败关闭。
- 准备阶段只证明内容与声明保持；Admission 单独检查全部工作源条件。
  默认 `declared_only`，显式用户工作解释只填补已证明未指定项，不修改原件/准备副本，不作色彩转换。
- 下游保留实际输出事实与工作解释归因。ProRes 全帧头、HEVC 全部 SPS/SEI 色彩观察及容器/逐帧交叉检查；
  不能以 FFprobe 合并结果或文件标签掩盖冲突；外部文件缺声明时记为继承，不伪造实测已知值。
- 新 Service 严格绑定同一 Project/Graph、session/CAS 和真实 Run/attempt。
  Studio 常驻显示选择和边界，准备成功但准入失败时允许仅更新解释并重新检查，复用有效准备产物。
  浏览器回归发现此路径误用 `run_all`；现改用精确绑定失败 Admission 的既有 `rerun_from_here`，
  不修改 Runtime 状态机或自动放弃旧运行。MP4/MOV 的格式从当前图恢复，防止面板重挂载默认 MKV 造成重复交付。
- 新候选本机状态通道为 `Studio-v0.3.4-color-candidate`；避免同产品版本旧技术包接管入口。
  不迁移/停止旧实例，不修改用户工程，不替换旧测试包。
- 新旧 T1 策略拥有独立发布开关，均保持 `False`；包能力清单不能声称未晋级策略已可用。
