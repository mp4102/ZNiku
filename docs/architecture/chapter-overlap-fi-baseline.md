  新处理方式是 **ZNIKU 的重叠 FI 扩展**，不得称为 AVEnhanceFlow 2.7.0 原有行为。

## 1. 解决什么问题

分章首先是为了控制单份 4K ProRes 的体积和外部 AI 处理批量，而不是只为寻找黑屏。目标流程：

```text
有效视频 → 按帧分章/分叶 → 逐叶增强 → 各章增强合并
                                         │ 本章及相邻章的增强帧
                                         ▼
                               各章 FI 上下文工作输入
                                         ▼
                                 人工外部 2× FI
                                         ▼
                               精确裁回各章负责的区间
                                         ▼
                        有序顺序读取 → 单次连续成片编码
                                         ▼
                              原始音轨封装 → 输出
```

该图只是模板展开的解释，不是固定 Core 拓扑。用户仍可编辑普通节点、连接、分支和参数。
不产生整片增强 ProRes 或整片 FI ProRes 作为必经中间产物；最终单次连续编码保持。
增强必须先按章合并，再准备 FI 输入。叶边界不再被当作 FI 的独立边界。

## 2. 当前行为与变更边界

当前源码 `avenhance_v27/template.py` 将精确帧值解释为下一章零基首帧；`exact_times` 只接受 canonical
有理秒字符串，不接受 `HH:MM:SS`。`single` 是整篇一章，目前没有平均 K 章 selector。

当前 `adapters.py::_program_filter` 对每章 FI 产物各执行一次 `tpad=stop_mode=clone:stop=1`。
旧 `planner.py`、`validators.py` 同时要求逐章 `2n-1`，所以不能只加裁边节点、继续接旧 ProgramEncode。

对总 N 帧、K 章，独立 FI 的总数是 `2N-K`，缺的是 K−1 个跨章插值时刻，并非 K−1 张原始帧。
旧逐章复制尾帧恢复了 `2N` 的时长，但不能提供真正的跨界插值。新链改为在章间保留真实上下文插值，
只在整片末尾保留一次明确的尾帧复制策略。

不修改旧精确定义的行为、旧 Run snapshot、旧收件目标或已登记结果。不从文件名或现有帧数推断旧成果
已经满足新合同。新旧节点不得通过修改版本字符串互相冒充。

## 3. 三种分章方式

本节的准备阶段身份规则继续约束 `0.3.2` exact definitions。经用户批准新增的
[`0.3.3` 原片规划与外部前处理](../v0.3.3-execution-plan.md)使用独立节点版本，将规划原片与
实际执行视频分开绑定；仅复用以下分章/分叶和重叠 FI 数学，不修改旧规则。

本节只适用于 `program` 的单个 admitted effective-video；N/FPS 仍来自已完成 preparation 的直接 Artifact，
不接受客户端自报。MR-off 使用 admitted Source，external MR 使用 admitted MR 输出；不在 MR 前预冻范围。

| 用户方式 | 输入及默认 | Python 规则 |
| --- | --- | --- |
| 平均分章 | 章数 K，默认 1 | 整数 `1≤K≤min(1000,N)`；禁止空章 |
| 精确时间分章 | 1–999 个 `HH:MM:SS` 时间点 | 正相对时间、严格递增；按 exact FPS 映射到最近帧，half-up |
| 精确帧分章 | 1–999 个整数切点 | 下一章零基首帧；严格递增，`0<F<N` |

999 是**切点数**，最多得到 1000 章。精确方式无切点时提示补充，若只要一章，应选择平均 1 章。
拒绝 bool、float、负数、未知方式、未知字段及不相干方式参数。禁止静默截断、排序、去重或吞掉空行。

### 3.1 平均分章

使用 `q,r = divmod(N,K)`：前 r 章各 q+1 帧，其余各 q 帧。由累计帧数生成边界。
任意两章长度差不超过 1，总和严格为 N。默认 K=1 的范围是 `[0,N)`。

例如 N=1801、K=3 得到 601+600+600；不先换算到整数秒，不按 GOP/原视频关键帧吸附。
旧工程 `single` 保持原状，不因新默认值自动改写。

### 3.2 时间与帧的解释

- 时间相对于有效视频首帧 0，不是播放器当前 PTS、墙上时钟或 SMPTE 带帧 timecode。
- 小时至少两位且不限制在 23；分/秒各两位、范围 00–59。第一版不加入毫秒、帧后缀或 drop-frame 记号。
- 新请求的时间文本由 Python 解析为 exact Fraction，再调用统一边界映射；不扩写旧 `parse_canonical_time`
  的接受集合，不让旧精确 Schema 悄然接受新字符串。
- 映射使用 `floor(T×FPS+1/2)`。前端同时显示原请求时间、实际切点帧号及对齐后的时间；
  `00:30:00` 在分数 FPS 下不保证恰好落在某帧起点。
- 输入时间有序但映射到重复帧、0、N 或越界，同样失败；指明具体行，不自动靠边或合并。
- 帧切点 899 表示第一章 `[0,899)`，第二章 `[899,N)`。N=1801 时是 **899+902**，不是每隔899帧切一次。
- 只读 preview 和正式 expand 都重验。选择方式/行编辑本身不创建 Run、Graph 节点、目录或媒体。

### 3.3 独立分叶：每段最长时长

章节区间始终连续、无重叠、无缺口、完整覆盖 `[0,N)`。章标签为 A…Z/AA…；章 ID 为 `chapter-0001`，
叶 ID 为全局连续 `leaf-0001`，章内 ordinal 独立从零计数。标签只展示，不是来源或执行身份。

用户设置为 **每段最长时长（分叶）**，字段 `leaf_max_minutes`，默认 **5分钟**，严格整数 **1–60分钟**。
这是叶的时长上限，不是固定切割间隔，也不是实际叶的最短时长；设置范围与实际片段长度必须分开说明。
一分钟甚至一帧的章，只要外部节点另行满足其能力要求，就保留一叶，不报“必须达到5分钟”。

Python 用 exact FPS 计算 `cap=floor(FPS×60×leaf_max_minutes)`；对每章 n 帧：

1. `m=ceil(n/cap)`，取不超过上限所需的最少叶数。
2. `q,r=divmod(n,m)`；前 r 叶各 q+1 帧，其余各 q 帧。
3. 叶长度差至多1帧，全部非空且不超过 cap；仅在本章内连续覆盖，不跨章，不移动章边界。

| 本章时长（以下例子为30fps） | 设置上限 | 实际叶 |
| --- | --- | --- |
| 30秒 / 1分钟 | 5分钟 | 各保留一叶 |
| 5分钟 | 5分钟 | 一叶 |
| 5分1秒 | 5分钟 | 2分30.5秒 + 2分30.5秒 |
| 11分钟 | 5分钟 | 3分40秒 × 3 |

不生成5分钟之后仅剩1秒的尾叶，也不自动合并不同章节。分数帧率必须向下取 cap，例如 `24000/1001`
下5分钟上限为7192帧；7193帧章需要两叶，即使仅略超过5分钟。预览展示实际帧数与时长，不隐性容差超长。
章切分与叶时长独立保存；修改任一项使相关媒体范围/节点输入发生变化时，按普通 DAG 规则 stale。
FI在增强叶合并成章后处理，叶数不会增加 FI 外部任务数。

已有 `AV27@0.2.1` 的正整数分钟、ties-to-even及固定长度加尾叶规则保持不变，不把新规则写回旧定义。
新预览最多10000叶，构造叶之前失败关闭；这是实现资源预算，不是 Core 语义或完整Graph传输能力保证。

### 3.4 分割与来源范围

Split 继续一次连续解码和 FFV1 全帧内编码，按帧边界产生 leaves，而不是在压缩源上粗略 stream-copy seek。
帧守恒不等于与原片像素相同：已有规范化缩放/像素格式仍生效；本次不重做图像配方。
不额外生成整章 `.mkv` 副本。章节是叶范围与后续整章增强文件的组织单位。

`pre_chaptered` 旧路径仍一 Source 一章并拒绝 selector。本版新重叠流程首先只支持单一 `program` 时间轴；
不能自动把不明连续性的独立源视为相邻帧。pre_chaptered 继续使用旧明确标识流程，不获得新重叠保证。

## 4. 三套坐标不得混用

| 坐标 | 单位 | 含义 |
| --- | --- | --- |
| 正式章 `[s,e)` | 有效视频源帧，0 基 | 该章拥有的原始帧区间，长度 n=e−s |
| FI 输入 `[a,b)` | 同一时间轴的增强帧，0 基 | 含上下文的工作区间，长度 M=b−a |
| FI 裁切 `[u,v)` | 外部 FI 工作输出帧，0 基 | 只选择本章负责的 2× 输出，不是源帧编号 |

`0≤a≤s<e≤b≤N`。非末章必须 `b≥e+1`；上下文只能来自真实、已验收的增强帧，不得用复制帧伪造邻章。
总 N、章范围、上下文范围及裁切规则都属于专用节点参数和已验证媒体 metadata，不成为 Core scope 或新 Plan。

## 5. 重叠与裁边数学

前提：选定外部模式对 M 帧产生 `2M-1`，输出时序相位为局部偶数位置对应输入时刻、奇数位置为相邻插值
时刻。**帧数正确本身不能证明相位正确**，外部适配实验必须独立验证这一前提。

以有效视频的半帧为全局单位，FI 局部第 j 帧对应全局 `2a+j`。

| 章节 | 局部保留范围 | 保留帧数 | 全局负责范围 |
| --- | --- | --- | --- |
| 非末章 | `[2(s-a),2(e-a))` | `2n` | `[2s,2e)` |
| 末章 | `[2(s-a),2(e-a)-1)` | `2n-1` | `[2s,2N-1)` |

每个内部边界的跨章插值帧由**左章**保留；下一章从自己的第一张原帧时刻开始。全片裁后序列严格覆盖
`[0,2N-1)` 一次，即 2N−1 帧。ProgramEncode 仅在最后复制一帧，成为 `2N` 帧、FPS=源 exact FPS×2，
时长为 `N/FPS`。内部章末不再 clone，不用总数相抵掩盖错裁、重复或空缺。

N=1801、切点899、仅展示右侧1帧数学最小上下文的例子：

| 章 | 正式范围 | FI 工作输入 | 原始 FI 数 | 裁后数 |
| --- | --- | --- | --- | --- |
| A | `[0,899)` | `[0,900)` | 1799 | 1798 |
| B | `[899,1801)` | `[899,1801)` | 1803 | 1803 |

合计3601，整片末尾补1得到3602。A最后保留的是源898与899之间的插值；B从源899对应时刻开始。
此例**不设置产品上下文默认值**；正式 Aion 工作输入可能需要更多左/右帧。

2026-09-13 已将 N=1…200、全部合法 K、左右同宽分别1/2/4帧的60,300组合转换为仓库可重跑测试，
裁后全局索引连续且唯一；另有非对称、多邻章、等长错裁等严格投影测试。实现位于
`zniku.chapter_overlap.context`，仅标识 `mathematical-only`，不代表外部工具验收或已注册生产profile。
实验的左右上下文及最短输入都必须显式提供，无模型默认值。构造投影前检查10000个来源交集预算；
超限拒绝，不截断或静默减少上下文。这是实验资源边界，不是外部模型能力上限。

## 6. 上下文策略与外部能力门禁

1. 右侧1帧只是提供跨章插值的数学下限，不承诺某个 Aion 模型只需要1帧上下文。
2. 2026-09-13 操作者声明外部 FI 软件版本 `v1.0`、模型 `Aion`，并批准先完成开发，真实能力实验统一移至
   Phase 5。软件版本不冒充模型版本。开发候选显式标记 `pending_real_acceptance`，采用待验的
   `even-input-2m-minus-1` 相位约定；左右上下文各32帧、最短输入2帧仅为可调整的工程候选默认值，
   **不是已测得的模型能力**。左侧可设0–240、右侧1–240、最短输入2–256；资源/几何限制仍独立严格校验。
   Phase 5 短样本须验证2×、相位、上下文和最短输入；失败时修订候选，不用猜测或放宽验证宣称通过。
3. 很短的章可能需要跨越多个邻章。准备节点必须显式连接与 `[a,b)` 相交的**全部增强章**，按时间轴顺序
   验证并取所需帧；不是只连接前后各一章。不能从相邻 FI/crop 结果取帧，否则可能产生循环依赖。
4. 全片首尾只能裁短可用上下文；不足外部工具最小要求时，明确拒绝该组合并说明可调整什么。
   一帧短片在数学上可定义，不表示外部工具已支持。禁止靠静默复制帧或改变切点伪装支持。
5. 任意边界不需要黑屏，但硬切镜头可能产生 AI 混合/重影；重复纹理、运动及模型边缘效应仍需主观复查。
   不承诺分段结果与整片 FI 逐像素相同，也不声称能从输出文件证明所用模型。
6. 开发实验应比较单章参考与多章结果的时序、首尾、切点附近运动/硬切；记录外部设置，至少选择一个
   通过的明确模式。失败时修订能力范围，不放宽 count/phase 或用内部复制帧掩盖。

## 7. 普通节点与验证职责

下列是节点职责，不是新增 Core 模型；精确身份见执行计划版本矩阵。Phase 1只实现独立规划和预览；
Phase 3同步实现新的Schema、六个自动adapter和八类validator，再注册可运行节点，不提供空壳执行器。

| 角色 | 直接输入 / 输出 | 必须校验 |
| --- | --- | --- |
| 新 selector / Split builder | admitted Artifact + 分章意图 → 静态 leaves/普通 Graph | 范围守恒、可运行前静态端口、exact输入绑定、严格Schema |
| 新 Enhancement / 章内 Merge | leaves → 本章增强 master | N不变、格式、模型声明、顺序及有效源Artifact/源坐标绑定；必须新精确定义 |
| FIContextPrepare | 有序增强章 → 单章带上下文 MOV | 单一时间轴、来源和范围覆盖、源帧数、输入格式/geometry/signal一致；无隐藏Artifact查询 |
| ContextFI external | 上下文 MOV → 原始 FI MOV | M→2M−1，模型声明、允许的相位profile、FPS/geometry/signal；仍显式检查/Submit |
| FICrop | 原始 FI MOV → 裁后章 MOV | 从上游已验证metadata重算u/v、输出职责范围、精确帧数；不只相信人工参数或总数 |
| 新 ProgramEncode | 有序裁后章 → 连续编码视频 | 每章边界与长度、全覆盖、仅全局tail1、exact FPS/PTS、编码能力与总数 |
| FinalMux / Output | 连续视频+原始源音轨 → 成片 | 原音轨、时长、名称、路径/覆盖；若旧validator限制producer类型，必须新精确定义适配 |

关键局部字段的存在理由：

- `source_frame_count` / exact FPS：定义同一有效视频时间轴，拒绝近似浮点。
- `chapter_start/end`：声明正式归属，防止每章 count 正确但整体位置错误。
- `context_start/end` 与有序输入片段映射：说明实际借用哪些增强帧，验证完整覆盖并算本地偏移。
- `crop_start/end` 或等价可重算参数：驱动实际执行；必须与直接输入metadata推导完全相等，不能任意裁一段等长内容。
- `context_profile` / 节点精确版本：绑定已验证能力、帧关系及实现，参与普通 reuse/stale。

不把 media path、陈旧客户端 probe、显示标签或 model declaration 当作真实来源证明。Frame range 的源坐标
不得被错误写成输出媒体的本地 frame range；命名清楚的局部 metadata 保留所需映射，由节点 validator 建立。
Phase 1核实：旧Enhancement输出有媒体与模型声明，旧Merge另有chapter ID/ordinal，但没有有效源Artifact身份
及完整源坐标绑定。因此新Split、Enhancement、Merge必须逐级传播并校验 `zniku.chapter.overlap` 局部metadata；
不能复用旧validator后从章标签推断来源，也不修改旧输出metadata来补齐。
新增 metadata 必须符合通用 Runner 的现有有界 JSON extension 协议；不另存 sidecar authority 或 Evidence。

首个Split的身份种子来自严格preparation服务：它核对当前Source/Admission/MR图与实际结果后生成参数。
Split自身再校验直接video/gate的UUID、N、FPS；后续新节点逐级校验同一绑定。旧Source/MR metadata没有
完整的video与原音轨lineage，所以不能声称仅靠这些字段已经证明任意自定义Graph的二者同源关系。
高级编辑若同时更换所有身份参数和同长异源的video/gate，仍需操作者负责源选择；本候选验收范围是
严格preparation生成的源配对，不包括抵御人为重新声明全部种子身份。未来强化应采用新版本局部合同，
不能修改旧精确定义或引入全局Evidence链。普通只改连接而保留绑定的误配仍失败关闭。

所有产生媒体的节点仍先验证进程成功（适用时）、存在非空、FFprobe及节点业务合同，再登记 Artifact。
精确媒体测试可使用短合成 frame marker / decoded hash oracle，但不把全片 hash 或 full decode 变成 Core 门槛。

  不能将合法自由图统称非法，也不能仅凭都是 VideoFile 就跳过业务检查。

## 10. 存储和规模必须实测

上下文只有几帧，并不意味着只需几帧磁盘空间。按章产生新 MOV 可能再占一份接近整章大小的文件，
裁后落盘也可能再占一份；需估算叶增强、章 master、context、FI raw、crop、编码和复制暂存的并存峰值。
界面区分“最大单文件估计”和“工作盘峰值估计”，注明格式/码率依据与误差；运行前以实际可用空间重验，
不足失败关闭，不清理上游、不自动改分章或换盘。控制单文件体积不等于总占用下降。

优先试验 ProRes 的逐帧精确 remux/裁边，验明时序与内容，不为加上下文默认再做有损增强章编码。
若当前工具不能无损、精确且资源有界地完成，需要报告该具体阻断，不暗中变配方。

新 Program 必须有界 argv 和顺序媒体消费，不沿用每章一个 `-i` 加上千解码器输入的旧实现。
Windows `CreateProcessW` 的命令行上限为32767字符（含终止符），见
[Microsoft 官方说明](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)。
若选择单输入 ffconcat 清单，必须满足 streams、codec、time base 等一致条件并处理精确duration/PTS，见
[FFmpeg concat 说明](https://ffmpeg.org/ffmpeg-formats.html#concat)。清单是 attempt 内受控执行输入，不是新计划权威。

999切点/1000章需覆盖 planner、预览、静态端口、Graph保存/重开、HTTP有限大小、UI列表/画布、上下文依赖
和真实合成 Program 顺序读取。当前4 MiB请求上限与旧200节点测试不证明可支持该规模。
允许经实测调整专用传输/显示的有限预算，但不得无限制放宽、隐性截断、删除节点或另造隐藏可运行图。
