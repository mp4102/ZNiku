# v0.3.4 缺失色彩声明：已批准政策与实测记录

日期：2026-09-14。状态：**第 6 节用户决定已批准，按独立合同实施；T1 仍未晋级**。
用户“接受，继续”批准显式工作解释；不是替任何真实素材作出解释选择，也不是授权写真实候选。
下文保留政策提出时的核查和实验事实；当前实现、验证及未关闭门禁以新增实施记录为准。

本文从属于[执行方案](v0.3.4-execution-plan.md)、[素材准备合同](v0.3.4-source-preparation-contract.md)
及唯一上位 [Graph Core](architecture/graph-core-baseline.md)，不新增 Runtime 状态机或另一张图。

## 1. 结论先行

**“能保留未指定色彩的时钟修复”与“能按确定色彩进入增强链”是两件事。**

已批准采用：

1. 准备阶段允许研究并验证“原样保留未指定声明”的窄策略，不猜 BT.709、不补标签、不改原件。
2. 保内容准备完成，不自动等于工作源准入；缺少后续所需色彩解释时，仍不能进入分叶／增强／FI。
3. 提供一次显式的“本工程工作色彩解释”选择：默认要求已明确；用户确有依据时可以采用
   SDR BT.709／有限范围／left 解释。该选择是用户决定，不是探测事实，也不是色彩转换。
4. 把原始观察、规范推导值和用户采用的工作解释分开保存。已明确冲突、未知解析状态、HDR 等不支持场景
   不能靠勾选继续；不能提供“强制通过所有检查”。

第 3 项是本次已批准的新增产品决定。本轮没有自动替任何真实素材作出该选择。

## 2. 为什么不能只删掉 unknown 报错

当前实现是一个固定 BT.709 limited/left 工作流。它不是任意色彩空间的透传管线。

| 位置 | 当前行为 | 直接放宽的后果 |
| --- | --- | --- |
| `source_preparation/inspection.py` | FFprobe stream 合并视图；缺字段记为 unknown；全帧扫描主要观察时钟 | 不知道字段真缺失、明确 unspecified，还是工具没读到 |
| `source_preparation/bitstream.py` | 只观察初始 SPS 的时钟 | 不证明全片色彩声明恒定，也不覆盖后续 SPS/SEI |
| `source_preparation/preservation.py` | 比较静态头属性、有序解码样本和音频 | 像素相同不能独自证明矩阵／传递／范围声明相同 |
| `source_preparation/adapters.py`、`models.py` | 准入直接构造固定 `SourceSignal()` | 若上游允许 unknown，会把未知写成已知 BT.709 |
| `prepared_source/adapters.py` | FFV1 分叶使用固定 setparams、色度位置及输出标签 | 后续不是单纯 stream copy，会采用特定解释 |
| `chapter_overlap/media_io.py`、AV27 encoder helper | Program 编码继续写入固定色彩和 VUI | 删除前置拒绝后，成品可能带未经确认的肯定标签 |
| `prepared_source/validators.py` 调用旧 signal helper | 某些外部输出的缺标签被按既定合同解释 | “继承工作解释”不能冒充“文件实际明确声明” |

旧链是在明确的工作色彩约定内使用这些行为；本次不回写或否定旧 exact 合同。
新增 unknown 例外必须处理上述依赖，不能只删除检查，或只删掉几项 FFmpeg 输出参数。

## 3. 事实层次：缺失不是解析失败

已批准的新局部合同逐字段保存以下事实；具体模型名及当前实现见第 10 节：

| 字段 | 为什么存在 |
| --- | --- |
| `source_layer` | 区分容器、H.264 SPS、逐帧解码观察；不把 FFprobe 合并结果当作某一层原始值 |
| `state` | 区分 `explicit`、`explicit_unspecified`、`absent`、`unavailable` |
| `raw_value` | 保存所属格式的实际值；同一个数字在不同格式中不一定同义 |
| `effective_value`、`basis` | 仅在规范推导条件已证明时记推导值和依据；不是猜测默认值 |
| `scope` | 明确初始头、完整帧扫描、全部适用参数集的覆盖范围 |
| `conflicts`／`changes` | 单独记录来源冲突或全片变化；不能用“有一个值可读”掩盖 |

这些事实只进入新版本局部合同，不在旧报告或旧 wire 里凭空补写。

两个容易混淆的例子：

- H.264 的有效 SPS 若证明相关语法未出现，FFmpeg 的 H.264 语法实现将 full-range flag 推导为 0，
  三项色彩描述推导为 2（未指定）；这不是推导成 BT.709。仅 FFprobe 缺字段还不能证明该语法条件。
  参见 [FFmpeg H.264 语法实现](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/cbs_h264_syntax_template.c)。
- Matroska 的 `Range=0`、chroma siting 的 `0` 表示未指定，不能与 H.264 full-range flag 的 0 混为一谈。
  Matroska 原色／传递特性的 2 也表示未指定。参见 [Matroska 元素定义](https://www.matroska.org/technical/elements.html)。

本政策不从“1080p”“yuv420p”“看起来正常”推导 BT.709，也不从未见 HDR 标签推导已证明 SDR。

## 4. 纯合成实验

只使用自动生成的 320×180、H.264/yuv420p、12 帧视频，无音频，不读取真实素材。
实验分普通重封装与指定 30 fps 两路；合成原时钟为 25 fps，故指定 30 fps **故意改变时间轴**，
用于隔离观察色彩／内容是否被改，不是合法 T1 正例，更不是帧率修复成功证明。

观察分为 FFprobe header、全部 12 帧色彩、压缩包／切片、Annex-B 整流、完整解码像素，
另用 MKVToolNix 的容器属性和 H.264 trace_headers 核对声明来源。
实测工具为 FFmpeg/FFprobe 8.1.2、mkvmerge 100.0；4 组共 12 个观察对象，68 条记录命令均成功。

| 样本构造 | 原始实际观察 | 两种重封装结果 |
| --- | --- | --- |
| FFmpeg 未传色彩参数的 MKV | 容器实际仍有 limited range；三项色彩描述未指定 | 未补三项描述，已有 range 保持 |
| FFmpeg 显式请求 unknown 的 MKV | 同样写入容器 limited range；H.264 `video_signal_type_present_flag=0` | 未把未指定项补成 BT.709 |
| 部分明确声明 | limited range、BT.709 matrix；SPS primaries/transfer 为 2 | 部分声明保持，未自动补齐其余字段 |
| 去掉上述 FFmpeg 容器、只保留同一 H.264 elementary stream | FFprobe 的四项色彩字段均未指定；容器色彩属性不存在 | MKVToolNix 首次封装仍未补色彩；没有把 range 猜成 limited 标签 |

上述每个文件均观察到 12 帧；各自两路输出的 H.264 切片、Annex-B 内容和解码像素保持一致。
容器样本的压缩包序列也一致；raw elementary 与 Matroska 包的表示不同，不用包字节直接相等作其依据。
这证明这些短样本上存在原样保持的可行路径，不证明所有缺声明视频均可安全修复或进入增强链。

本地脚本、工具版本、逐条 argv 和原始观察保存于 ignored
`build/missing-color-probe-20260914-01/`，不是产品 CLI，也不会提交合成媒体和工具日志。
实验没有音频、真实长片、HDR、复杂 SPS 切换或外部 AI；这些未测范围不得写成已通过。

MKVToolNix 文档将 `--default-duration` 定义为改变默认时长及轨道时间戳；色彩设置另有独立参数。
实验没有使用色彩覆盖参数，也没有启用改码流时钟选项。
参见 [mkvmerge 参数文档](https://mkvtoolnix.download/doc/mkvmerge.html)。

## 5. 已批准的窄“原样保留”政策

| 情况 | 保内容准备 | 工作源准入 |
| --- | --- | --- |
| 完整明确 BT.709 limited/left，且观察一致 | 按原策略检查 | 保留当前要求 |
| 原色／传递／矩阵确实 absent 或 explicit unspecified | 保留同等未指定状态，必须完成下列验证；策略启用另受真实晋级门禁 | 未明确工作解释前不能继续 |
| range／chroma 缺失 | 保留；有有效语法证据时才记录规范推导值 | 未解决的项仍需明确决定；不能套用跨格式数字默认值 |
| 原先明确，候选丢失或变成 unspecified | 拒绝，不以像素相同放行 | 拒绝 |
| 原先未指定，候选强加 BT.709／HDR／full-range | 拒绝等价修复；这是新增解释或变更 | 不能伪装成原件事实 |
| 两层明确冲突、全片声明变化、非法／保留值、解析失败 | 不属于缺失声明例外 | 拒绝 |
| HDR／ICC／colour-remapping 等未支持语义 | 本次不扩大范围 | 拒绝；另立策略 |

允许例外前的证据必须补齐：

1. 有界读取真实容器字段与相关 H.264 参数集，保留 presence 和原始值；未知解析状态失败关闭。
2. 在已有完整帧扫描中聚合色彩与相关 side data，检查中途变化；补足全部适用 SPS/SEI 的覆盖。
3. 检查原件和候选完整帧序／像素、所保留音轨、时间关系及声明关系；保内容不能仅靠相同头值或 N/FPS。
4. 新增声明元素只有在准确符合已证明的格式规范等价规则时才可接受，并记录差异；
   不把任意 absent→known 或“这个播放器默认这样”列为等价。
5. 保持受限进程、取消、EOF、空间、排他输出及输入前后身份门禁；失败不登记可用媒体。

源、诊断、准备及准入仍是普通节点。准备 validator 不运行未来 Admission；准备输出登记后，
Admission 再读取真实输入并检查当前工作解释和音频绑定，不构造未来 Artifact ID。

## 6. 工作色彩解释：已批准的唯一新增用户决定

默认模式：`declared_only`。信息充分时按实测声明继续；不足时等待，不预勾选“按 BT.709”。

可选模式：`operator_confirmed_bt709_limited_left`。只对已证明“未指定而非冲突／解析失败”的字段适用。
用户确认本工程采用固定 SDR 工作解释；已有明确字段必须与该解释兼容，不能被此选项覆盖。
首版不提供任意色彩转换器或可自由填写不受 Schema 约束的值。

产品必须直接说明的含义：

> 这个文件没有完整注明处理所需的色彩信息。修复工作副本可以保留这种状态，
> 但后续增强和编码需要确定的色彩解释。只有你确认素材适合按 SDR BT.709 处理时，才选择继续。
> 这不会证明原片本来就是 BT.709，也不会改写原件或保内容修复副本。

确认影响必须完整说明：后续派生的分叶和成品会按该工作解释处理并标注；它不是原件颜色的测量结论，
也不是将另一种已知色彩空间正确转换为 BT.709。无法确认时保留阻断，使用外部专业确认或另建新工作源。

分开记录：

- `observed_signal`：原件／工作参考的实际声明及不确定性，不能被用户选项修改。
- `working_signal`：本工程后续处理采用的确定解释。
- `interpretation_policy`、`basis`：来自明确声明、规范推导还是用户采用；保存策略精确版本。
- `inherited_interpretation`：外部增强/FI 产物缺标签时，按当前已绑定的工作解释验收；
  不写成“文件自己已明确声明”。显式冲突仍拒绝。

选择必须属于同一 Graph 的严格节点参数，而不是仅写 UI preference 或一个可绕过检查的浏览器布尔值。
改变它时下游按现有规则 stale；需要新的 Run/attempt，不接管正在等待的外部任务。

## 7. 实施与版本边界

本轮不直接改 `SourceSignal()` 默认值、外部 validator 或旧 encoder helper 的语义。
新的报告／准入字段及变更语义的节点必须用新的 exact definition 和局部合同版本，保留旧版本含义；
不能把 dev3 创建的旧 snapshot 无声解释成新政策。产品版本保持 `0.3.4`，开发线仍为 `codex/v0.3.4`；
新政策节点使用 exact `0.3.4-color.1`。这不是新产品发布，不另建分支或发版。

按已批准决定，依次实施：

1. 冻结字段、适用范围、允许的声明等价关系及新 exact 版本；同步 Python Schema 和 corpus。
2. 实现容器／参数集／全帧观察及反例，不先删除旧拒绝条件。
3. 分开时钟准备适用性与工作色彩准入，仍受其他视频／音频约束。
4. 在准入节点和 Studio 加显式工作解释选择；适配 MR／Split／外部输出／Program 的局部绑定。
5. 运行合成三路线、旧合同、Schema、Studio、打包门禁，再明确真实代表和留出。
6. 取得精确真实输入、策略、输出目录的写授权后验证；全部要求通过才晋级 T1。

不新增全局色彩 authority、Compiler 或 Runtime 业务分支；也不扩展为通用转码器。

## 8. 必须覆盖的反例与验收

- unknown→强补 709、known→unknown、limited→full：raw 像素相同也不得误报等价。
- 容器 709 与 SPS 另一矩阵；工具合并只显示其中一方时仍能发现冲突。
- 中间 GOP 改色彩／range 后再恢复，或中途出现 HDR／ICC／相关 SEI：首尾一致不能放行。
- 缺省值、explicit unspecified、未观察到、非法值彼此不能互相归一化。
- Matroska 的 0 与 H.264 的 0 按各自字段解释；不跨格式套表。
- 一层 absent、一层合法明确且一致，不误判为冲突；同时保存两层事实。
- 默认 declared_only 下未明确输入仍阻止；确认选项不能覆盖显式冲突或音频失败。
- 工作解释变更造成下游 stale；另一工程、旧 attempt、外部任务产物不得串用。
- 正常源无需复制；准备副本不加猜测标签；下游采用的标签只能归因于已绑定工作解释。

本节是验收要求，不是测试成绩单。当前实现和已经完成的验证分别见第 10 节及实施记录，
没有以旧实验、合成通过或测试中临时打开 T1 代替真实晋级。

## 9. 政策批准前的历史诊断增量（dev4 快照）

本节保留批准前的事实，不代表当前源码仍只有诊断文案。dev4 不含新色彩解释政策。

- 仅改善 `E_SOURCE_PREPARATION_VIDEO_PROFILE_UNSUPPORTED` 的 message：逐项指出探测未确定的字段，
  与已知不支持值分开；明确“不等于损坏、不自动补标签放行”。原错误码、拒绝 predicate、T1 候选判断不变。
- 新增 13 项纯数据诊断测试；独立审查通过。结合内核、对抗输入和 Service 的回归共 **77 passed**。
- Ruff/format、Windows/Linux 目标 mypy（229 文件）、Schema/corpus 一致性通过；
  诊断更新的 dev4 技术包重建并审计通过，未包含第 6 节建议的新选项。完整顺序见[实施记录](v0.3.4-phase0-4-implementation.md)。
- 未修改 Studio 源码或旧节点定义；本次没有真实候选写入，没有处理用户工程或重启用户服务。
- T1 仍禁用，Phase 2／Phase 4 的交付阻断尚未消失；本稿不能替代真实代表／留出验收。

第 6 节已批准的核心决定是：**允许“原样保留未指定声明”的准备结果，
但只有工作色彩已明确，或用户显式采用受限工作解释后，才进入后续处理。默认不替用户采用。**

## 10. 批准后的实现与边界

- 新 `source_color` / `prepared_color` 共 18 个 exact `0.3.4-color.1` 定义，与旧 18 个 `0.3.4`
  定义共存。旧定义完整形状由固定回归测试保护，产品版本仍为 `0.3.4`。
- `ColorField` 保存原值、状态及依据；`ObservedSignal` 保存容器、完整 SPS/SEI、全帧观察，
  `SourceGate` 另存工作解释及 5 项逐字段依据。聚合有界且核对真实层级，不保存全片帧表。
- MKV、MP4/MOV 容器直接读取原始字段；源 H.264 参数集及逐帧扫描到 EOF。
  中途变化、层间冲突、未知扩展、HDR/ICC、不支持的 SEI 或解析失败均不能靠用户选项覆盖。
- 保内容准备验证实际视频帧序/像素、全部音轨和声明保持；不应用工作解释、不为副本补猜测标签。
  准备成功后独立 Admission 再判断色彩及其他输入要求，二者不互相冒充。
- 新 T1 `/2` 有独立发布开关，当前保持 `False`。旧 `/1` 的能力开关不能为新策略授予资格。
- 下游既保存实际输出观察，又保存继承工作解释的标记。ProRes 逐包读帧头、HEVC 扫描完整 SPS/SEI；
  自动输出事实绑定实际 stat，外部文件在显式验收时观察，不信任第三方成功声明。
  FFprobe 的合并 header 不冒充原始容器声明；FFV1 的无相关码流字段事实与容器字段分开记录。
- 新 Service `/prepared-color/` 与严格 wire `0.3.4-color.1` 绑定真实 session/Run/attempt/CAS。
  Studio 默认 `declared_only`，必要选择常驻；改变解释写入同一 Admission 节点，普通新 Run 复用仍有效的准备结果。
- 色彩技术包使用 `Studio-v0.3.4-color-candidate` 状态通道，避免同为 0.3.4 的旧技术包接管新入口；
  不迁移旧状态、不替换旧包、不操作用户服务。

技术验证及候选产物持续记录在[实施记录](v0.3.4-phase0-4-implementation.md)。CPU 合成编码测试不是 GPU/NVENC
或真实外部 AI 验收；未知外部 SEI 仍会拒绝。没有执行真实素材修复，也没有替任何真实工程选择工作解释。
