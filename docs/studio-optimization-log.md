## UX-001：本章收件自动预选

### 用户要求

“确认本章收件匹配”应根据序号自动匹配并选好来源文件，用户可以自行更改。
正常的一章多叶交付不应要求每个下拉框重新选择一次。

### 现状与原因

2026-09-21 在 Chrome 中只读观察到：某章有 5 个待交回目标，5 个候选文件均保留正确章节和
`leaf-0001` 至 `leaf-0005` 编号，但外部软件追加了 `_slp` 后缀。匹配窗口的全部来源下拉框仍为
“本次不收件（稍后补件）”，显示“未自动匹配”，已选数量为 0。

当前服务端在 `src/zniku/project_service/handoff_batch.py` 中按完整规范文件名忽略大小写匹配；
仅后缀不同也无法自动关联。匹配窗口位于 `apps/studio/src/studio/components/HandoffBatch.tsx`。
现有 `tests/test_handoff_batch.py` 还覆盖“仅规范名自动匹配”；后续需同步调整建议匹配测试，
不能因此放宽收件绑定和媒体验收测试。
这是匹配便利性不足，不是已证明候选媒体不合格；本次未替用户选择、确认收件或提交节点。

合成示例：

| 候选来源 | 应默认选择的本章目标 |
| --- | --- |
| `Example (2026).B.leaf-0001_slp.mov` | `Example (2026).B.leaf-0001.enhancement.mov` |
| `Example (2026).B.leaf-0002_slp.mov` | `Example (2026).B.leaf-0002.enhancement.mov` |
| `Example (2026).B.leaf-0005_slp.mov` | `Example (2026).B.leaf-0005.enhancement.mov` |

### 后续实现方向

1. 仅在当前 handoff 的目标及此次已选/本章收件候选内匹配。保留完整规范名匹配，并补充明确章节标识
   及 `leaf` 序号的识别；外部软件追加的 `_slp` 等处理后缀
   不应使仍然清晰、唯一的分叶对应关系失效。具体允许的命名语法在实施时用合成测试明确。
2. 序号指文件名中可识别的分叶编号，不是文件选择顺序、目录枚举顺序或字母排序；不得把年份、模型版本、
   分辨率等其他数字当作分叶号，也不按大小、修改时间猜测对应关系。
3. 对明确、唯一且属于当前章的匹配，打开窗口时直接预选来源，更新已选数量；不是仅显示推荐文字。
   正常 5 份全部对应时应显示已选 5 份。
4. 每行仍可更换来源或改为“本次不收件（稍后补件）”，标示“已自动匹配”“已手动调整”“待确认/冲突”。
   同一预览内刷新展示不得静默覆盖用户手动选择；候选或任务绑定失效时明确提示重新核对。
5. 缺号保留未选，允许其余无冲突文件分批交付；同号多候选、编号含混、显式跨章、未知目标或同一来源
   被分配给多个目标时，不自动猜选，并给出具体冲突原因。缺少足够章节/编号信息时仍允许人工映射。
6. 已有收件目标不因自动匹配被静默替换；覆盖仍沿用明确确认。匹配建议由 Python Project Service 生成，
   Studio 展示并编辑预览选择，不新增一套前端文件匹配权威。
7. 自动预选不等于确认收件、媒体验收或完成节点。确认前不复制、移动或重命名；取消不改文件。
   收件后的整章检查及“提交本章并继续”仍分别显式执行，文件名不证明实际内容归属。

## UX-002：收件名称与路径说明不清

### 用户反馈与现状

“来源文件 → 某章某叶.enhancement.mov”及其下方长 UNC 路径没有解释各自角色，
用户无法判断是在选择什么、文件来自哪里、是否需要手工更名或复制，以及确认后会发生什么。

核对 `HandoffBatch.tsx` 与 `handoff_batch.py`：

- 标签箭头右侧取自 `row.target_name`，是系统为该分叶约定的接收后名称，不是所选来源文件名。
- 下拉框中的候选才是用户已处理好的文件；这里的“来源”不是原始视频素材。
- 裸露的 `row.target_path` 指向本任务的 `outputs`，是整章检查通过后的成果位置，
  不是当前候选所在位置，也不是要求用户手工投放的 `incoming` 收件目录。
- 当前流程是确认收件后先复制/原位收纳到 `incoming`；整章检查通过后发布到 `outputs`；
  用户再显式提交，才登记 Artifact 并推进节点。仅显示路径不代表文件已经存在或检查通过。

因此，不应只把箭头换个方向；需要分开说明文件角色、操作结果和发生时机。

### 后续展示方向

每行以用户要交付的处理段为标题，例如“B 章 · 第 1 段（共 5 段）”，不以长文件名做标题。

1. **选用处理好的文件**：展示实际候选文件名和可修改的选择框，配合 UX-001 自动预选。
2. **接收后文件名**：单独展示系统采用的规范名，说明由系统整理，无需用户预先手工改名。
3. **本次文件操作**：依据实际来源展示，而不是统一写含混的“原位收纳”。
   - 外部目录来件：“复制到本章收件目录，保留所选原件”。
   - 本章收件目录来件：“在本章收件目录内更名/整理，不另留原名副本”。
   - 已在正确收件位置：“使用已有文件，无需复制或更名”。
4. **检查通过后保存位置**：简洁显示“本章增强成果目录”，完整路径放入“查看文件位置”折叠区。
   折叠区分别标明“所选文件位置”“收件位置”“检查通过后保存位置”，不得混用。
5. 窗口简述明确：“为每一段选择对应的处理结果。确认后先接收文件；整章检查通过后，
   再由你提交并继续。”不暗示确认匹配就完成节点，也不把本章增强成果称为最终成片。

交互说明示例（合成名称）：

- 处理段：B 章 · 第 1 段（共 5 段）。
- 选用处理好的文件：`Example (2026).B.leaf-0001_slp.mov`。
- 接收后文件名：`Example (2026).B.leaf-0001.enhancement.mov`。
- 文件操作：在本章收件目录内更名；整章检查通过后转入本章增强成果目录。

此项只优化说明及信息层级，不借机改变现有收件、检查、发布、提交的先后顺序。

### 验收清单（尚未执行）

- [ ] 无需展开完整路径即可看懂“本行是哪一段、选了哪个文件、接收后叫什么、是否保留原件”。
- [ ] 完整路径有角色标签并默认折叠，不再裸露在匹配状态后面；长路径不撑破窗口布局。
- [ ] 明确区分收件目录与检查通过后的成果目录，不引导用户往 `outputs` 手动投放。
- [ ] 对外部复制、本章目录更名、无需操作三种情况显示真实文案，覆盖风险继续单独提示。
- [ ] 界面及无障碍名称使用清晰中文；预选、取消、检查失败和最终提交的原有边界不变。

## UX-003：统一操作状态与下一步提示

- 采纳日期：2026-09-21。
- 状态：用户已采纳方案；本次只记录，尚未实现或验收。

### 用户困扰与现状

用户以 C 章批量增强交付为例反馈：选择文件、确认收件、整章检查、提交都可能耗时，
但没有弹窗时主要依赖按钮状态或处理记录判断，容易被误认为卡住，引发重复点击或其他误操作。
自动合并虽显示百分比，仍缺少一眼可见的进度条。

现有代码有局部状态文字和按钮忙态，并非完全没有反馈；问题在于反馈分散、层级不明显。
`use-handoff-batch.ts` 能区分收件和检查等阶段，但全局反馈主要传递忙碌布尔值；
`TaskDrawer.tsx` 主要展示 Run/NodeRun，`WorkflowNodeCard.tsx` 的确定进度主要以百分比文字显示。
收件、检查和提交期间的本机操作，没有形成连续、明确的“已接到操作 → 正在做什么 → 下一步”引导。

### 已采纳的展示方案

1. **常驻单行状态栏。** 升级现有底部独立任务摘要行，不新增悬浮遮挡面板。用户无需展开处理记录，
   即可看见任务/章节名称、当前操作、忙碌或待操作状态，以及下一步提示。查看详情沿用现有任务抽屉，
   需要执行下一步时定位到对应操作区，不在全局栏复制一套同权重提交/重试按钮。
2. **三处一致反馈。** 常驻栏回答“整体现在该等还是该操作”；节点卡片显示该节点进度；右侧操作区
   立即反馈“正在请求/等待服务响应”，得到服务端确认后才显示“已受理/正在处理”。三处使用正确绑定的
   同一状态来源，不各自猜测结果。
3. **按可测量性选择表现，不按步骤大小。** 有真实字节数、帧数等测量时显示进度条、百分比和已用时；
   没有可信测量时显示轻量动态标识、具体操作文字和已用时，不按时间编造百分比或剩余时间。
   缺少可信服务端开始时间时只标“请求等待时间”，不把浏览器等待当作实际复制/检查耗时。
   当前批量接口没有字节级复制/逐文件检查进度，首版不得把本地忙态冒充这些测量。
4. **节点增加细进度条。** 合并等自动节点复用已有真实进度，保留百分比，保证缩放后可辨识且不改变
   节点身份、运行结论或画布几何稳定性。不把“已完成步骤数/总步骤数”冒充媒体处理百分比。
5. **完成后明确下一步。** 收件完成提示检查，检查通过提示提交；提交成功后展示实际后继状态。
   下游仍依赖其他章节时说明等待原因，不能承诺已开始执行。百分比达到 100% 但尚在校验/登记时，
   明确切换为收尾阶段，不提前显示节点完成。
6. **等待用户与系统忙碌分开。** 外部任务需要用户交付时显示“需要你操作”，不持续转圈或倒计时；
   收件/检查属于交回操作，不表示外部 AI 正在增强，也不将 `waiting_external` 伪装成 Runtime `running`。
7. **防误操作但不锁死工作区。** 处理中禁用重复提交及与当前操作冲突的动作，并说明原因；
   保留查看、缩放等安全操作。其他任务是否可操作遵从现有服务互斥规则，不由 UI 自行放行。
8. **多任务和异常明确归属。** 展示具体活动项及其他活动/待操作数量，不轮播抢焦点，不相加不同任务的
   百分比。当前查看的历史与实际活动任务分开；切换视图不改变工程会话、Run、NodeRun、handoff 绑定。
   断线或迟到响应显示“状态暂未更新，操作结果待确认”，保留最后可信状态，不无限假装正在处理，
   不把切换视图当取消，不自动重试可能已经生效的收件或提交。

### 实施边界与及时性

复用现有任务投影和轮询所有者；必要时补充本机交回操作的展示信息，不新增 Runtime 状态、任务数据库、
隐藏队列或节点内部恢复能力。收件、整章检查及显式 Submit 的职责与原有顺序保持不变。

此前观察到的 NAS 场景进度反馈滞后纳入本项检查：同步进度消费/数据库访问及日志缓冲是待验证因素，
不是已经确认的唯一瓶颈。应分别观察媒体执行、进度接收、UI 更新和收尾，防止只是把旧百分比画成进度条。
不凭 UI 体验修改媒体合同、关闭校验、搬迁真实工程或调低网络安全设置。

## PERF-001：FI 上下文准备减少整章重复 I/O

## PERF-002：裁边职责保留，默认不再落盘整套裁后 ProRes

### 目标及边界

独立裁后章保留为可选真实输出。单遍时基只做有界实验，失败保留安全导出，不阻断融合主路线。
