## 1. 本次要交付什么

让用户在分章、增强和 FI 之前，知道源视频能否可靠进入工作流；确有兼容问题时，默认推荐适用的内置修复，
由用户确认后生成工作副本。内置能力不适用或失败时，允许使用同一个外部任务助手导入修复结果。

修复针对封装、时间戳和音频时间关系，不是画面增强，也不是马赛克修复（MR）。界面统一称为
“素材检查与准备”，内部修复能力按普通节点开放，高级节点图仍可自由编辑。

交付承诺分成四项：

1. 正常源可直接使用，不强制复制、重封装或转码。
2. 不把“不符合本工作流要求”误称为“文件损坏”，明确解释问题、影响和可选办法。
3. 至少一种窄范围内置修复完成真实代表样本、留出样本及下游准入验证，才宣称内置修复交付。
4. 外部修复有明确输入、专属收件目录、验证标准及提交动作；不支持的结果不会绕过准入。

不是“自动修好所有视频”。没有可靠方法时，明确停止并保留原件，比生成无法证明正确的工作源更重要。

### 2.3 已有证据，不等于已实现能力

授权普查覆盖 47 个同类实体视频；全部完成 EOF 扫描，只有 1 个通过当时全部局部准入条件。
这不代表其余 46 个损坏：其中多数是时间轴或目标合同不兼容，另有实际解码错误、音频 priming 和属性歧义。
类别可能重叠，不能简单相加成“坏文件数量”。

该批样本集中在 1080p H.264/yuv420p 与 AAC，不能外推到 4K、HDR、HEVC、隔行或复杂多轨。
公开仓库只保留匿名类别、结论和合成 fixtures；原始路径、片名、调查日志及逐文件报告留在本地，不提交 Git。

独立项目 VideoSourceRepair / `repair-video-source` 0.1.0 已完成工具与技能交付；其候选生成命令仍明确返回
`candidate_created_unverified`。既有合成测试、调查报告和一次成功修复个案，都不替代 ZNIKU 内置策略验收。

## 3. 范围与红线

本版本包含：只读诊断、已验证的保内容工作副本策略、外部保内容修复导入、新输入型准入、工作参考与音频绑定、
Studio 交互、持久存储、打包与限定真实验收。首发面向单一 program 参考时间轴。

本版本不包含：

- 原片更名、覆盖、替换或自动删除；批量改写媒体库；自动迁移旧工程及外部等待任务。
- Runtime 业务分支、隐藏 Graph、Compiler、Freeze、Revision authority、全局 checksum/QC/Evidence/receipt。
- 任意 shell、脚本插件、浏览器传入命令模板、自动执行大模型生成的代码。
- 节点内部 resume、修复检查点、静默跳过失败、自动切换正在运行的 snapshot。
- 自动补帧/丢帧凑 N、猜测源帧率、默认改速、默认转音频、默认裁剪静音或删除音轨。
- 把 MR、Enhancement 或 FI 的主观画质判断混入源视频兼容修复。
- GUI 控制外部 AI 软件、联网上传视频、修改 AVEnhanceFlow 或依赖本机 skill 路径运行产品。
- 扩展为通用转码器、万能损坏恢复器，或在未授权情况下执行整个调查库的修复。

完全无法被 FFprobe 识别的文件不能登记为 MediaFile，也不能为了诊断绕过 Source validator。
此时入口明确报错，提供外部诊断说明；用户得到可识别文件后，选择“作为新工作源”重新导入。
首次 probe 前须校验所选单文件实体路径/后缀并限制 demuxer/protocol，随后核对实际容器和流布局；
不能先展开网络或播放列表再事后拒绝。此限制属于新业务入口，不静默修改旧 Source definition。

## 4. 四种来源，分别负责什么

| 来源角色 | 含义 | 影响哪些下游 |
| --- | --- | --- |
| `original_media` | 用户最初选择、只读保留的原件 | 诊断、保内容比较、默认音频来源与用户追溯 |
| `reference_media/reference_video` | 原件或修复副本，经新准入后形成的工作参考 | N、精确 FPS、分章切点、分叶区间、MR 输入基准 |
| `effective_video` | 实际进入分章分叶的参考视频，或可选 MR 的合格输出 | 分叶、增强、合章、重叠 FI、裁边和连续编码 |
| `audio_sources` | 显式选择的原件音轨载体，或另行验证的音频准备输出 | 最终音频映射、时间关系、封装；不使用 MR 文件附带音频替代 |

绑定规则：

- 规划依据新准入后的 reference N/FPS，而不是浏览器填写值、未修复原片的错误 PTS 或候选文件名。
- `original` 与 `reference` 不同，不意味着启用 MR；用明确 `mr_role` 和实际直接输入表达。
- 音频载体默认仍是原件，无需先抽轨；其原视频不满足 CFR，不等于该文件中的音频一定不可用。
- gate 只绑定已有直接输入 Artifact ID、策略和声明的参考坐标；不预填未来输出 UUID。
  后续节点从已登记的 reference/effective 直接输入建立本地绑定。
  具体区分 gate 的 `reference_media_artifact_id` 与 Admission 完成后登记的
  `reference_video_artifact_id`：后者不能提前写进 gate，也不能与前者互换。
- 修改 reference、音轨选择或修复策略时，按普通参数/输入变化使相关下游 stale；不继承旧外部交付承诺。
- 不查询隐藏的媒体索引补齐依赖，不递归构造全局来源证明链。局部 metadata 只能描述节点实际消费的关系。
- 原件、修复副本和 MR 输出即使 N/FPS 相同，也不能仅据此宣称内容等价。

## 5. 建议节点及合同

新 profile 固定为 `zniku.prepared-source-overlap@0.3.4`，局部 namespace 为 `zniku.source.prepared`。
以下职责和端口已在 Phase 0 细化；完整 exact identity、字段和失败边界见[合同冻结记录](v0.3.4-source-preparation-contract.md)。

| 节点 | 输入 → 输出 | 职责和失败语义 |
| --- | --- | --- |
| 原件入口 | 无 → `MediaFile` | 复用 SourceMedia 的只读机制；实体容器白名单在本路线明确校验，不跟随播放列表 |
| SourceDiagnostics | `MediaFile` → `DataFile` | 完整检查得到事实与建议；素材不兼容可以是成功的诊断结果，检查未完成则失败 |
| BuiltinSourceVideoPrepare | `MediaFile` + 诊断 `DataFile` → `MediaFile` | 执行闭合策略；候选生成和保内容验证都通过，才登记媒体输出 |
| ExternalSourceVideoRepair | `MediaFile` + 诊断 `DataFile` → `MediaFile` | 普通 manual_external，单一媒体输出；显式导入并通过同等级保内容验证 |
| SourceAdmission | `original_media: MediaFile`、`reference_media: MediaFile`、`audio_sources: ordered_many<MediaFile>`、诊断 `DataFile` → `VideoFile` + gate `DataFile` | 输入型准入；验证工作参考和选定音频关系，建立可规划的局部绑定 |
| SourceAudioPrepare（条件项） | 原件 `MediaFile` + 诊断 `DataFile` → `MediaFile` | 仅在独立音频策略晋级后提供；MKA 载体及明确音轨映射，不把一种转换冒充通用修复 |
| prepared-source 下游定义 | reference/effective 视频、gate、显式音频及现有有序视频端口 | 按新绑定执行 MR、Split、增强、Merge、Context、FI、Crop、Program 和 Final |

SourceAdmission 的输出 VideoFile 是已验证输入的只读视频引用，不要求复制整个文件。
音频多轨映射通过严格 Schema 与有序输入表达；无音频源的行为须明确声明，不凭缺失音轨自动变成静音成片。

外部节点首版只声明一个单值 MediaFile 输出，保持现有文件导入能力边界。MP4/MOV/MKV 使用固定格式的
exact variants；检查实际 demuxer 和流布局，不以改扩展名伪装格式，不顺便重编码。

旧 AV27 `0.2.1`、overlap `0.3.2`、source-aligned `0.3.3` 的 Schema、validator、绑定语义全部保留。
凡消费或输出新绑定的节点使用新的 exact definition；可复用分章数学、FFV1/ProRes/编码 helper，不能冒用旧版本。
无需新语义的通用节点不随产品版本一并升级。

## 6. 流程与选择

```text
选择原件 → 普通 Source → 素材检查
                           │
             ┌─────────────┼─────────────────┐
             │             │                 │
           可直接用     内置保内容准备      外部保内容修复
             │             │                 │
             └─────────────┴─────────────────┘
                           ↓
                 新工作源准入（含音频关系）
                           ↓
                 分章/分叶与处理设置确认
                           ↓
                  可选 MR → 增强 → 重叠 FI → 编码
原件音轨／已验证音频准备输出 ───────────────────→ Final
```

上图是用户可选择的建图路线，不是 Runtime 条件路由。每次选择由 Project Service 显式编辑同一 Graph；
检查、准备和完整处理可以分为多个普通 Run，仍使用当前 Project.graph 及各自普通 snapshot。
失败后切换外部方案或重试，创建新的 Graph 配置/Run/attempt，不修改正在运行的 attempt。

| 选择 | 使用条件 | 不允许的捷径 |
| --- | --- | --- |
| 直接使用 | 诊断与新准入均通过 | 只因 FFprobe 能打开就跳过业务准入 |
| 内置修复工作副本（默认推荐） | 有已启用且匹配全部前提的策略；用户确认空间与处理成本 | 因为是默认选项就自动写文件，或忽略独立的音频阻断 |
| 导入外部保内容修复结果 | 用户已完成外部处理；可证明所承诺的内容保持 | 只检查 N/FPS，或把 skill 报告当通过凭据 |
| 作为新工作源 | 内容/N/时长改变，或无法证明与原件等价，但新文件自身可用 | 将新文件塞进旧等价槽、继承旧分章与外部任务 |

“作为新工作源”首版建议新建工程：重新 Source、检查、准入和规划；旧工程及原件不改。
它不是“强制通过修复验证”，也不承诺原片 N、音画对应或旧 Artifact 仍可复用。

## 7. 诊断：区分事实、建议与准入

### 7.1 最小报告

诊断 DataFile 是普通版本化业务输出，严格拒绝未知字段，至少包含：

- `schema_version`、直接输入身份及检查前后 stat、工具版本、检查范围、完成标记。
- 视频流/音频流布局、精确有理数率、time_base、geometry、SAR、方向、场序及色彩声明。
- 完整解码/packet 计数、raw PTS 缺失/重复/逆序、展示顺序、best_effort 差异、EOF 和解码错误。
- 容器总时长、视频观察首尾/帧覆盖分别记录；不把两者混成一个 duration。
- 每音轨的有效时间关系观察值、skip/discard/priming 提示及未能确定的项目。
- 多个 findings：稳定 `code`、证据、对目标合同的影响、适用策略或不支持原因。
- 各检查阶段实测耗时、已扫描帧/包、可用的资源统计；未知值明确 unavailable。

`PTS + nb_samples/sample_rate` 得到的解码观察终点，不自动等于已经扣除 padding 的可听终点。
报告不能把未完成的音频语义检查填成通过，也不输出无依据的“可修复概率”。

### 7.2 成功与失败

“检查完成，发现不兼容”可以完成诊断节点并产出报告；问题未解决，或当前 reference/audio 仍不符合合同，
后续 SourceAdmission 才拒绝。原件 findings 保持原样；修复后的准入重新检查当前 reference/audio 与对应关系，
不要求修改旧报告使其显示通过。诊断报告是事实记录，不是独立的准入 authority。
超时、取消、工具缺失、报告损坏、输入变化或未达到要求的扫描范围，属于检查未完成，不能登记成功报告。

GUI 可显示诊断严重程度，但不新增 Runtime 的 `warning_policy` 或“带警告成功”状态。
允许哪些媒体进入后续流程，由对应节点合同和用户明确选择的图决定。

## 8. 内置策略：可扩展，但不能一次全部启用

策略由固定 `strategy_id/version`、前提、允许变化、执行器、验证器和测试集合构成。
报告可列出研发方向，只有发布时已验证的 allowlist 能运行；不提供绕过验证的试验开关给普通用户。

| 类别 | 当前成熟度 | v0.3.4 处理 |
| --- | --- | --- |
| 正常源；视频终点与容器时长差异 | 已有正常和 duration 边界证据 | 正常不处理；先纠正新合同的时长取值，不能无故修媒体或放宽所有容差 |
| T1：固定近似时钟/有限抖动 | 有窄范围候选工具，尚无本版本真实修复验收 | 首个内置交付目标；完成前提、完整比较、真实代表和留出测试后启用 |
| T3：重复/逆序 PTS 重建 | 存在成功个案，无通用映射证明 | 默认不启用；另行证明展示顺序、末 GOP/B 帧和包/帧对应，不硬编码某片偏移/尾帧修补 |
| AAC priming/edit-list 保持 | 可识别，尚无本批通用通过路径 | 保留独立阻断；先研究不改编码内容的封装保持方案，通过专项才启用 |
| PCM/FLAC 音频准备 | 尚属转换方案，不是现成保真能力 | 条件项，不作自动 fallback；冻结表示和变化承诺并通过专项才加入产品目录 |
| 明显非均匀时间轴、载荷错误、计数或 SAR 歧义 | 已有反例，未有安全通用策略 | 解释并拒绝内置保内容修复；提供外部诊断/新工作源路线 |

### 8.1 T1 的最小前提与验证

必须同时满足：

1. 固定实体容器、视频编码、音轨布局和工具范围；首版从普查覆盖的 SDR 逐行 H.264 场景建立白名单。
2. 完整 EOF、无解码错误、无缺失原始 PTS；N 与包/展示关系满足该策略明确支持的模式。
3. 目标 FPS 是明确有理数，来源有依据；不得仅凭 `r_frame_rate` 或近似小数猜选 30/1 与 30000/1001。
4. 没有需要 T3 映射的重复/逆序，也没有明显非均匀时间轴；有限抖动逐帧满足冻结的误差模型。
5. 目标与原观察首尾跨度差不能超过策略限额；“不超过一帧”只是必要条件，不是内容/同步充分条件。
6. 用户确认写入新的候选目录；工具、空间、输入身份和输出排他条件检查通过。

修复节点完成前必须分别得到以下结论：

- 原件未变；输出可完整识别和解码，N 与展示顺序保持。
- 完整有序解码视频表示与应保留的属性一致；不能只比较文件大小、N 或压缩包数量。
- 声明保留的全部音轨，其内容与首尾时间关系满足策略；不因视频通过就忽略音频。
- 输出目标时钟、容器语义通过共享的纯媒体检查函数；不遗留码流/容器冲突。

上述检查在准备节点内部完成，不执行或等待下游 SourceAdmission。准备输出登记后，独立 SourceAdmission
节点再消费真实直接输入，核对绑定及完整工作源合同；未通过时不得进入规划。两者可复用检查函数，
不能形成循环依赖或预造未来 Artifact。真实策略晋级还必须通过这条实际下游准入路径。

比较内容时使用独立的帧序/校验时钟，避免坏 PTS 让校验进程自身漏输出尾帧；这是节点内验证方法，
不是重新定义媒体时钟。未验证候选保留在 attempt staging，不能提前登记为可被下游消费的 Artifact。

### 8.2 不能混为一谈的工具行为

FFmpeg `fps` filter 可以复制或丢弃帧，因此不作为本策略的保 N 时间戳修复捷径。
参见 [FFmpeg fps 文档](https://ffmpeg.org/ffmpeg-filters.html#fps)。

MKVToolNix `--default-duration` 会修改轨道时间戳，不只是修改标签；能生成文件不代表展示顺序、码流时钟和
音画同步已经正确。参见 [mkvmerge 官方文档](https://mkvtoolnix.download/doc/mkvmerge.html)。

FLAC 的整数 PCM 无损性不自动证明 AAC 浮点解码转整数后的逐样本等价。涉及量化/抖动时必须单独声明；
本版本不以“转 FLAC 就无损”作为准入依据。参见 [FLAC 格式规范 RFC 9639](https://www.rfc-editor.org/rfc/rfc9639.html#appendix-A)。

## 9. 音频：独立于视频修复的门禁

默认保留原音频及其相对视频的关系，不默认抽轨，也不取 MR/enhancement/FI 的附带音频。
Final 使用显式 `audio_sources` 和轨道映射；其音频检查不得再次要求音频载体中的旧视频先满足 CFR。

需分别核对：压缩首包、skip/discard/edit-list、首个有效样本、有效样本数量、末样本及相对 reference 的偏移。
负首包 PTS 或 AAC 编码延迟本身不是损坏，不能统一丢首包、裁 1024 samples 或强制全部轨道从 0 开始。

研究次序：

1. 原编码/封装保持：证明原 AAC 的有效样本语义在目标封装和工具组合中保持。
2. 如第一种不可行，再研究显式音频准备：固定采样表示、位深、通道、舍入/抖动、映射与同步承诺。
3. 转换路线只能作为新的已验证策略和独立 SourceAudioPrepare 节点；声明是转换，不承诺原压缩字节不变。
4. 若上述策略未晋级，v0.3.4 对相关素材继续拒绝；UI 给出原因和外部选择，不显示已支持 priming。

音频专项未完成，不阻止已声明且不含该问题的 T1 范围交付；但所有音频专项必须标为不支持/延期，
不能将“源视频修复完成”扩写成“所有来源均可全链路运行”。

## 10. 外部修复交付

外部任务沿用现有体验：自动建立当前 attempt 收件目录，用户可直接复制文件，或在 UI 选择文件复制导入；
发现文件只提示候选，必须“检查并提交”才尝试登记输出。

- 外部输入说明包含原件、问题、目标精确率、允许变化与不允许变化；不附可直接执行的任意命令。
- 提交文件进入独立 attempt；实际格式、输入身份、当前任务、冲突路径和文件稳定性均重新检查。
- 内置和外部“保内容修复”使用相同的内容保持标准；不会因为来自外部工具而只查容器/N/FPS。
- 外部有损重编码若无法满足精确保内容标准，提示其应使用“新工作源”，不能称为等价修复通过。
- 失败保留具体原因、原件和已复制文件；不自动推进，不把外部等待计为外部软件的真实运行进度。
- 切换交付格式/输入/策略后创建新 attempt；旧目录及待交付文件不能串入新任务。

VideoSourceRepair 只提供可供用户调用的外部诊断与修复知识。它的 JSON、日志或成功声明不是 ZNIKU 准入凭据；
导入必须按当前文件重新验证。用户可选择导出脱敏的问题说明，ZNIKU 不自动调用大模型或上传媒体。

## 11. Studio 操作布局

保留已确定的四个基本输入：素材组织方式、视频素材、工程名称、工程保存位置。
不因加入修复能力再增加必填路径；工作数据默认位置及高级存储逻辑保持一致。

在现有分析步骤内增加“素材检查与准备”区，而不是要求用户回到未知节点手动找报错：

1. 先显示检查进度；初步 header 结果明确为初步结果，不提前显示“可运行”。
2. 正常素材显示“可直接处理”，继续现有处理与成片设置。
3. 有问题时显示“哪里不符合要求 / 会影响什么 / 推荐怎么做”三块简明信息。
4. 适用时默认选“内置生成工作副本”，显示原件不改、预计额外空间和需要完整验证，再由用户开始。
5. 无内置方法或失败时提供“导入外部修复结果”“作为新工作源”“返回选择素材”，不逼用户无限重试。
6. 修复与工作源准入均完成后，才按新的参考 N/FPS 进入分章/分叶设置和完整图确认。

“高级详情”只折叠 packet/PTS 数值、工具版本、命令日志和详细轨道信息；必需的处理选择、阻断原因、
预计空间、来源变化和下一步操作直接可见。不得再次把必填参数藏进折叠区。

进度显示阶段名、已处理帧/字节、实测速度和已耗时；有可信分母才显示百分比/预计时间。
检查、复制、重封装、内容验证、音频核对分别计时，不把“候选写完”显示成修复 100%。
取消沿用 attempt 取消与新 attempt 重跑语义；UI 保持可操作，服务异常不能造成整个网页锁死。

返回步骤不改变运行图。改源或已确认的准备策略时明确提示下游将失效；已在等待外部交付的任务不暗中替换。
新旧工程打开后都显示自己的 exact profile，不自动升级。

## 12. 工作数据、空间和归档

继续使用工程旁 `.data` 或用户选择的专用数据盘及现有可读目录分配器；不创建第二套 UUID 目录体系。
每个检查、准备和外部修复 attempt 有独立目录，示意结构中的名字只负责可读性，不作为执行身份：

```text
<工程>.data/
  attempts/common/
    素材检查__N002/R001-A001/reports/source-check.json
    内置素材准备__N003/R002-A001/staging/...
    内置素材准备__N003/R002-A001/outputs/<标题>.source-prepared.mkv

```

这些编号为合成示例，实际编号由现有 allocator 分配并持久绑定；内部正式身份仍是 UUID。
新节点的 `common` 存储提示在 Phase 0 固定；不迁移旧布局，不并行发明另一套 run/attempt 标识。
继续遵守现有路径长度预算、危险组件和链接检查，不截断媒体名或悄悄改到系统盘。
原件默认是只读外部依赖；保存工程和工作副本不代表已经归档了原件，UI 应提醒用户保留源路径或另做显式归档。

成功工作副本、报告、外部产物默认长期保留，不自动清理；失败 partial 标明不可用，也不删除用户收件或原件。
清理只能走现有受限 attempt 目录规则及明确操作，不能把数据目录当缓存整棵删除。

空间预检展示“原件不额外复制”“候选媒体”“可能的导入副本”“日志/报告”各项；重封装只能给估算，
不得承诺文件大小固定。空间不足、磁盘断开、输出冲突均停止且不登记媒体输出。

不生成整篇 4K ProRes 来做源修复，也不改变现有按章/叶限制大中间产物的设计。

## 15. 分阶段执行及退出条件

### Phase 1：可运行的诊断与工作源准入

产出：普通 Source → Diagnostics → 新 SourceAdmission 的真实 Python/Project Service 路径；
新报告、来源/音频合同和测试；正常源通过，异常源产出可理解诊断但不放行。

### Phase 2：第一种内置修复及独立验证

产出：T1 候选生成、staging、完整内容比较、目标时钟与音频关系检查；成本统计和失败保留。

若无策略通过，本阶段不标完成，不用按钮/候选命令替代交付。T3/音频转换未晋级仍关闭。

产出：单输出外部修复节点与导入合同；新 prepared-source MR/Split/Merge/Context/FI/Crop/Program/Final；

退出条件：正常、内置、外部三条合成链均能进入分章/增强/FI/Final；输入变更与重试正确 stale；
不同 reference/MR/audio 的产物不能混用。保留原音频的事实由实际 Final 检查证明，不仅检查图连线。

### Phase 4：Studio 与桌面候选包

产出：素材检查与准备交互、修复/验证真实进度、导入和拒绝说明、返回/改源行为、可读工作目录和独立候选包。

候选包必须标明实际启用策略及不支持范围。

### Phase 5：限定真实全链路验收

产出：在明确授权的有限素材上完成正常、内置修复、外部保内容导入以及不支持拒绝；至少一条已修复源完成
分章/分叶 → 外部增强 → 章内合并 → 重叠 FI → 裁边/编码/Final，并由用户检查成品。

退出条件：原件保留，reference/effective/audio 绑定正确，已启用策略的真实验证和下游结果均通过；
成本可复核、失败可解释、旧工程未被修改。自动化不得替代真实外部 AI 软件和用户成品验收。
未获真实处理授权或未收到外部产物时，标记等待相应验收，不假报完成。

替换正在使用的候选包分别处理，不因一次代码授权自动发布或重启服务。

| R04 重复/逆序 | 本版本拒绝路径；如要启用另立代表与留出 | 单例尾部补丁不是通用算法 |
| R05 AAC priming | 合成隔离测试 + 真实拒绝；启用前另做完整专项 | 负首包不等于损坏，也不允许忽略音频问题 |
| R06 明显非均匀时间轴 | 至少 1 个真实拒绝样本 | 保 N 改成另一节奏不能宣称保时长/同步 |
| R07 载荷解码错误 | 真实拒绝 + exit=0 的合成损坏反例 | 不把“进程正常退出”当全片无错误 |
| R08 属性/计数歧义 | 真实拒绝 + 独立 SAR/计数合成反例 | 不直接改标签或凑帧放行 |

首发只启用 T1 时，最小真实候选写入集合为 R02/R03 各一个开发和一个留出，共四个文件；其他先只读或拒绝。
四个文件对应两个子范围都启用的目标；如只晋级其中一类，该类仍需一个开发和一个留出，另一类须明确标为
未交付，并同步缩窄公开支持矩阵，不能宣称本节双类别目标全部通过。
真实路径映射和授权留本地，不进入公开文档；修复授权须明确源、策略和新工作目录，普查授权不等于写授权。

“留出”指该策略实现冻结前未参与候选生成调参的文件，不代表其普查统计从未见过。
若根据留出结果改算法，该文件转为开发样本，须补充新的留出；不得重复调参后仍宣称独立验证。

### 17.2 性能报告要求

逐阶段记录头检、全扫描、候选生成、视频内容比较、音频比较、准入及下游运行，不用单次重封装时间代表总成本。
至少报告：墙钟耗时、输入/输出大小、读取遍数、可测的 CPU 时间/峰值内存、处理速度和存储类型。

磁盘物理 I/O、功耗或 GPU 未测则写未测；不能从文件大小估算成实测 I/O。区分冷/热缓存、源盘和工作盘、
工具版本、并发数、完整与局部扫描。大文件额外读取通常是验证成本，不能为了快而只测头尾再称完整内容保持。

首次真实代表默认串行，避免共享磁盘争用和失去归因；有测量后再决定并行预算。
本版本不承诺固定“几分钟修完”，也不把同类 1080p 测量外推到 4K 全库处理。

6. **外部区分保内容修复与新工作源。** 前者严格验证，后者新建工程重新分析，不继承旧产物。

9. **每种启用策略有版本、前提、反例与晋级条件。** skill 可持续扩展，但产品不直接信任其结果或执行其命令。
10. **按 Phase 0–5 推进，真实写入和成品验收单列。** 至少一条真实修复链通过后才标记本版本交付完成。
