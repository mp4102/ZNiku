# 外部马赛克修复交回体验增量

- 状态：实现与本地自动化门禁完成，用户已授权 commit/push；真实 NAS 与操作者体验待验收。
- 日期：2026-09-16；产品版本保持 `0.3.5`。
- 上位权威：[Graph Core](architecture/graph-core-baseline.md)；展示遵守
  [Studio UX](architecture/studio-ux-baseline.md)，目录遵守
  [英文可读工程目录](english-readable-storage-plan.md)。不增加 Core 状态、动态端口或第二份 Graph。
- 本次不操作真实工程、NAS、媒体或运行服务，不自动升级旧节点、等待交接或已有候选包。

## 1. 目标与操作顺序

操作者负责选对处理结果，系统负责检查、规范命名和收纳。新流程为：

1. 查看待处理视频与素材信息；分析报告不再与视频混成两个需要外部处理的普通输入。
2. 在外部软件处理完整视频，保持帧数、帧序、等价帧率、画面尺寸和信号合同。
3. 选择处理结果：放入交回目录后刷新，或从原位置选择文件。此时不复制、不改名。
4. **检查并导入**：在原位置只读检查，通过后才收纳到当前任务的 `incoming`。
5. **提交并继续**：显式提交时转存到当前 attempt 的正式输出区，重新执行节点检查，通过才登记 Artifact。

文件出现、刷新、选择和检查通过都不自动完成节点。服务不声称凭文件属性证明实际使用了某个 AI 模型，
也不声称已证明逐帧内容一致或主观画质。

## 2. 素材与报告展示

主区域区分“待处理视频”和“素材分析报告”：

- 视频显示实际文件名、位置和已登记的尺寸、帧率、帧数等信息。
- `admission.json` 显示为中文标签的分析摘要，帮助操作者理解它是参考分析，不是外部处理素材。
- 完整 JSON 放入高级详情，使用缩进格式化并提供复制/查看能力；不改写历史分析文件。
- 报告来自当前 Run 直接输入绑定，读取有界；缺失、过大或无法解析时明确提示，不猜测报告内容，
  不把展示结果变成新的媒体准入 authority。

## 3. 新 exact 与文件名

新增 `zniku.source-admitted.mosaic-restoration.external@0.3.5`，保持 `video`、`gate` 两个输入和固定
`video` 输出。它仍是普通 `manual_external` 节点，不是源故障修复节点。

新节点实际容器由媒体内容识别，首批支持 MP4、MOV、MKV，不用候选扩展名证明容器。
正式归档名取**当前直接视频输入**的文件名，去掉最后一个扩展名后加 `.RM` 和实际容器扩展名。例如：

| 当前视频输入 | 外部实际容器 | 规范归档名 |
| --- | --- | --- |
| `Example.repaired.mp4` | MP4 | `Example.repaired.RM.mp4` |
| `Example.repaired.mp4` | MOV | `Example.repaired.RM.mov` |
| `Example.repaired.mp4` | MKV | `Example.repaired.RM.mkv` |

不从工程片名或候选任意名称覆盖当前输入 stem；不偷偷转码，不把 MOV 直接改成 `.mp4`。
`declared_container` 在新 exact 中仅为兼容向导 wire 的初始建议，展示为高级“建议输出封装”，不限制实际交回容器。

初始 handoff 中的目标是建议位置；候选检查后的实际路径通过已有 `ManualSubmission/ProducedOutput`
提交同一个固定 `video` 端口。新路径只允许位于已绑定 attempt 内，不改写既有 handoff、Run snapshot 或端口。
Runtime 不理解 MR 业务，媒体合同由此新节点的 validator 负责。

## 4. 两种交回方式的统一行为

| 来源 | 第三步选择 | 第四步检查通过后 |
| --- | --- | --- |
| 当前任务 `incoming` 中的视频 | 刷新、识别实际媒体；单候选可预选，多候选必须明确选择 | 已规范命名则原地保留，否则在该收件区规范命名，不复制一份大媒体 |
| 原生选择器选择的其他位置 | 只记录此次授权选择；展示来源和将来的归档位置 | 复制到当前任务 `incoming`，保留外部原件 |

交回目录按当前项目存储绑定定位，例如 `Example.data/source-repair/round-001/incoming`。
不要求用户提前使用规范名，不按目标扩展名过滤本次候选；实际媒体仍必须受支持并通过本节点合同。
观察只扫描有界单层目录，不递归遍历任务根或 NAS。目录中多份候选不按名称、修改时间或体积猜选。

检查期间显示明确的检查状态；复制期间显示实际字节进度，不伪造媒体扫描百分比或剩余时间。
检查不通过时说明失败原因，候选仍留在原位置；不先复制巨型文件再告知合同不符。
已有同名收件或正式文件必须显式确认替换，未确认不得覆盖。

最后“提交并继续”只需同一 attempt 内转存，不再复制第二份大媒体。正式输出区同时出现不同容器的多份
规范结果时拒绝猜选；操作者必须明确解决冲突。发布文件仍不等于 Runtime 已完成，完整节点检查后才登记结果。

## 5. 兼容与恢复边界

- 旧固定 MP4/MOV/MKV exact 的强制封装语义不变，旧 0.3.3 的 CFR 规则不放宽。
- 旧工程、正在等待的 handoff、已登记产物和历史目录不自动改名、迁移或替换；新交互能力由新 exact
  的完整身份识别，不能只凭显示名称套用。旧任务继续使用其原交回合同。
- 已实现旧 0.3.5 固定封装的只读候选检查 helper；它仍限制原声明容器，不授权改写旧正式目标或旧 snapshot。
- 新节点 producer metadata 明确记录新身份与实际容器；下游显式识别，不冒充旧生产者。
- 选择、检查任务和 UI 票据是有界进程内交互信息，不持久化为 Runtime 状态、checkpoint 或验收凭据。
  重开应用后重新读取文件、检查；不能把过期页面中的成功状态当作正式提交依据。
- 检查后文件或输入绑定变化必须重新检查。正式 Submit 始终复验；失败仍遵守整节点新 attempt 的既有规则。
- 中断复制可能留下独立暂存文件，未登记为 Artifact；不自动清理用户原片、历史结果或整个工作数据目录。

## 6. 文件与执行安全

浏览器仅传原生选择句柄或本任务目录候选句柄，不提交任意源/目标路径作为写权限。
每次写入前重验工程会话、Run、最新等待 NodeRun、handoff、端口与 attempt 持久绑定。
拒绝符号链接、junction、重解析目录、非法文件组件和路径逃逸；避免覆盖共享硬链接目标。

外部位置的文件只读检查后复制，保留原件；只有当前 attempt 自己的直属 `incoming` 候选可以改名或转存。
复制先写本次独立暂存，完成并确认源文件没有变化后发布；不直接截断已有目标。失败清理仅限本次创建的
暂存文件及空目录。Windows 收件/发布不依赖 NAS 的硬链接支持。

检查与复制期间服务维持互斥，状态仍可轮询；不得同时切换工程、再次提交或正常退出应用。
本次不增加强制 checksum、全局 full verification、证据链、分布式锁或跨进程事务。常规 stat 比较只用于
检测可信本地环境的常见文件变化，不承诺发现恶意保持属性的内容替换。

## 7. 验证与交付门禁

自动化至少覆盖：

- 实际输入 stem 命名、MP4/MOV/MKV 内容识别、任意候选名、错误 N/FPS/几何/信号拒绝。
- 旧 exact、旧 waiting、旧 metadata 不被放宽；新下游按明确新身份消费。
- 选择无写入；检查失败原件不动；通过后分别执行收件区改名和保源复制。
- 多候选不猜选、同名覆盖需要确认、候选变化/过期会话/错误绑定拒绝。
- 复制异常、发布失败、重复点击及响应丢失后的安全恢复，不凭票据或文件存在自动完成节点。
- 中文报告摘要、格式化 JSON、新交回界面、类型和 Python/TypeScript wire 一致性。
- Python 相关和全量测试、类型与质量门禁；Studio 测试、typecheck、生产构建；合成短媒体与浏览器验收。

真实 NAS、实际外部软件产物、巨型文件复制和操作者体验仍待人工验收。自动化通过不能宣称这些真实场景
已完成；不为测试自动启动、关闭或替换用户正在使用的应用。

## 8. 本地候选与人工验收入口

本增量在 `codex/chapter-batch-enhancement` 上实现，版本仍为 `0.3.5`。最终本地候选为：

```text
build/desktop-mr-intake-20260916-r2/dist/ZNIKU Studio/ZNIKU Studio.exe
```

这是新的完整目录，不覆盖此前英文目录候选。构建时 Git 基点为 `bcc8488`、工作区包含本次增量，
`BUILD-INFO.json` 如实记录 dirty 构建及精确输入内容；不能把候选说成旧基点的原样包。
打包核对覆盖 114 个 Python 模块、115 份源码文件、7 个前端资源和 4 份媒体工具/许可文件。
没有启动该包或改变用户现有服务。未创建 tag、Release 或合并 main。

验收顺序：

1. 若已有 `0.3.5` 候选运行，先在其页面使用“退出应用”。单实例机制不会因双击新目录自动换掉旧进程。
2. 保留候选整个目录，双击上述入口；不要只复制 exe。
3. **新建测试工程**，使用默认 `0.3.5` 流程，启用“外部马赛克修复”。旧等待任务仍使用旧合同/按钮。
4. 确认输入视频名及可展开的报告；用任意名的已完成视频测试目录刷新和原生选择两种入口。
5. 确认选择时没有复制；“检查并导入”通过后才收纳，外部原件保留，再“提交并继续”。
6. 若文件已发布但页面中断，可展开恢复说明，用“检查已收纳输出”重新检查后提交，不重新复制。

自动化使用纯合成文件和独立服务，没有验证用户的真实 NAS 工程。不要用仍在写入的视频作为来件；
复制中检测到来源增长或属性变化会中止，不发布结果或沿用检查成功状态。
